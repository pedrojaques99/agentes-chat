# 0119. agentes.chat as a remote MCP server for AI apps

- Status: Accepted
- Date: 2026-11-01
- Code: `packages/db/src/schema/apps.ts` and migration `0170_ai_apps.sql`; `packages/engine/src/apps/` (`urls.ts` addresses and scopes, `clients.ts` DCR, CIMD and how an app is shown, `oauth.ts` authorize, consent and tokens, `grants.ts` the bearer gate, Settings and personal tokens, `tools.ts` the six tools, the waits and the MCP handler); `packages/engine/src/net-guard.ts` (`fetchPublicDocument`, `pinnedLookup`); `apps/server/src/routes/oauth.ts` (discovery, `/api/oauth/*`, `/mcp`), `apps/server/src/routes/app/apps.ts` (consent and Settings API); the `via` line in `packages/engine/src/context.ts`; tests `apps/server/test/oauth.test.ts`, `mcp.test.ts`

## Context

People already work in their own AI app: a game developer in Unity or Blender asks Claude for help all day. Asking an agentes.chat agent for something means leaving it. Linear and Notion solved the same problem with a remote MCP server: the person pastes a URL into Claude, ChatGPT, Cursor or Claude Code, signs in, and the app can act for them. We want the same: "send this task to the marketing agent" from the local Claude, and the answer comes back.

## Decision

1. **A stateless remote MCP server at `PUBLIC_URL/mcp`.** Short, never changes, and the OAuth resource identifier. Streamable HTTP, POST only (GET and DELETE answer 405), JSON answers with a `Content-Length` (ChatGPT refuses a chunked JSON answer), no SSE and no session. `@modelcontextprotocol/server@2.3.1` (exact pin, Apache-2.0) serves the 2026-07-28 protocol (`server/discover`, which ChatGPT uses for every request) through `createMcpHandler` in JSON mode, and the 2025 protocol (`initialize`) through a stateless transport set to answer JSON. One `McpServer` per request, from the principal. The v1 SDK stays for the outgoing connectors.

2. **Our own minimal OAuth 2.1 authorization server**, ported from Dinzo's (TypeScript, on Bun), not `@better-auth/oauth-provider` + `@better-auth/cimd`. Better Auth stays the session of the consent page. Why:
   - a token must belong to one workspace (`org_id` on every row, a live membership check on every call); the provider binds a workspace only through the session and issues JWTs, whose revocation lags by up to an hour, and with a database read per call a JWT buys nothing;
   - at MillionSend the provider needed about eight hooks, each one a production bug (`offline_access` injection, scopes pinned at registration, resource seeding, host-bearing custom schemes, metadata sanitising, client updates, expired consents, tokens outliving their consent);
   - the CIMD fetch needs an SSRF guard either way;
   - its table names collide with the outgoing connectors' `oauth_clients` and `oauth_states` (ADR 0016).
   The cost is security code of our own, covered by Dinzo's test list and MillionSend's and Real Oficial's edge cases as tests.

3. **Discovery.** `/.well-known/oauth-protected-resource` and `/.well-known/oauth-protected-resource/mcp` (Claude asks the second first, ChatGPT documents the first) serve the same RFC 9728 document; `/.well-known/oauth-authorization-server` and `/.well-known/openid-configuration` the same RFC 8414 one (no OIDC scopes, no id_token). `issuer` has no trailing slash and every address comes from one helper (`appsUrls`), so the metadata, the challenge and the address in Settings can't drift. `offline_access` is never advertised: refresh tokens are always issued, and the scope is dropped when sent. CIMD needs both `client_id_metadata_document_supported` and the `none` auth method advertised (Claude picks CIMD only then); the only auth method is `none`. Both documents are cacheable for an hour. A missing or bad bearer gets 401 with `WWW-Authenticate: Bearer resource_metadata="…/mcp", scope="read write"` and a JSON-RPC error `-32010` carrying the same challenge in `data.www_authenticate` and `_meta["mcp/www_authenticate"]` (a bare 401 may not start ChatGPT's sign-in).

4. **Clients.**
   - **CIMD** (an https `client_id`): https with a path, no user, fragment, IP literal or localhost. Fetched through `fetchPublicDocument`: every resolved address public, the socket pinned to one (IPv4 first, no fallback), the `lookup` answering Bun's `all: true` form with an array (Dinzo: `results.sort is not a function`), no redirects, 3 s, 64 KB, `application/json`. The document must name its own address, with 1 to 10 return addresses under the DCR rules; `private_key_jwt` connects as a public client with PKCE. Three fetches at a time, six waiting, then "busy"; a good copy kept 5 minutes, a failure 20 seconds (in memory), a copy under a day old used when a refetch fails.
   - **DCR** (`/api/oauth/register`): JSON up to 16 KB, 1 to 10 return addresses of at most 512 characters, no fragment: https, http on `localhost`/`127.0.0.1`/`[::1]` (no `application_type` needed: Cursor and Grok Bot send none), or exactly `cursor://anysphere.cursor-mcp/oauth/callback`; every other custom scheme refused. Cursor's three addresses register in one call. Always `none`. Only a cleaned name (no control, invisible or direction characters, 64 at most) and the return addresses are kept: never a logo, a home page or pinned scopes, so nothing else an app claims reaches a consent screen.
   - A loopback return address matches on scheme and path whatever its port (RFC 8252 §7.3), across the three loopback names.
   - `/api/oauth/authorize` sends parameter errors (response type, PKCE, resource) back to the app only once it has been issued a token; before that they stay on `/autorizar?erro=pedido_invalido`, since anyone can register any https return address and the endpoint would bounce links through this domain (RFC 9700 §4.11.2).

   | App | Way in | Notes |
   |---|---|---|
   | claude.ai, Claude Desktop, the phone | CIMD or DCR, `https://claude.ai/api/mcp/auth_callback` | One connector serves all three. |
   | Claude Code, VS Code, Gemini CLI | DCR, loopback (VS Code 33418, moves when busy) | Shown as "a program on this computer". |
   | Cursor | DCR with three addresses | `cursor://` shown as Cursor; 8-hour access tokens (its refresh is reported flaky). |
   | ChatGPT | CIMD with `private_key_jwt` | Public client with PKCE; QA gate G3 before its card ships. |

5. **Tokens.** Opaque: `aga_` access (1 hour, 8 for Cursor), `agf_` refresh (90 days, sliding), `agp_` personal, each 43 base62 characters; only sha256 is stored (enough for 32 random bytes, and it survives an `AGENTES_SECRET` rotation). Codes: 120 seconds, used once by an atomic update; a replayed code revokes every family it minted. Each family carries the access it was consented with and its access-token lifetime, fixed at the code exchange from that request (`app_tokens.scopes`, `access_seconds`): one app on two computers keeps each connection's own, and the `/mcp` gate enforces the family's within the grant's. Refresh rotates in a family: a rotated token presented again within 60 s while no pair it minted has been refreshed is a client's retry (two calls refreshing at once) and gets a sibling pair, the earlier ones left alive; the first sibling refreshed revokes the others; anything later revokes the family; an expired or revoked one is refused and leaves its family alone. The access token before a rotation stays valid until it expires (clients refresh with calls in flight). `/api/oauth/token` takes forms only, answers `no-store` and OAuth JSON even on a crash; `/api/oauth/revoke` always 200.

6. **One connection is one workspace**, picked on the consent page (`/autorizar?req=`, the web app's), the form's `orgId` checked again on the server (member, not paused). A grant per person, workspace and app, shared by its connections (disconnecting ends all of them; its scopes are the widest of theirs); connecting again reactivates it and revokes every token it had. Every revocation (Settings, a removed or departed member, a password reset, 90 days unused, a personal token revoked with itself) goes through `revokeAppGrants`, which takes the tokens and audits each grant. How the app is shown is computed from this request's return address and stored on the grant (Dinzo: the first registered address showed): `verified` (a CIMD document on a known app's own host), `https` (the return host, or a CIMD document's host anywhere else, its name unverified and checked), `loopback` ("on this computer", whatever document it names: any local program can present a known app's `client_id` with its own port), `app_scheme` (Cursor). A brand mark only from a verified address; an unverified name holding claude, chatgpt, openai, cursor or agentes off that vendor's host is flagged. A request answers once: a second answer (Back, a link scanner) is 409 and revokes nothing. Allowing sends the person an "App conectado" email, and so does giving a live connection write access (`apps.scopes_changed`).

7. **Tools act as the person.** `send_to_agent` (write), `wait_for_reply`, `list_agents`, `list_channels`, `read_conversation`, `list_recent_tasks` (read), through the engine calls the apps make, so every check is the person's own. None decides an approval, changes a setting or manages people; write tools aren't even listed for a read grant. A sent message carries `meta.via` (`{ kind: "app", grantId, name, brand, host }`, never accepted from a client), the agent reads "(sent by X through Y, an app connected to agentes.chat; the reply is read there)", and the send is audited (`apps.message_sent`). It also carries `meta.readOutside` (ADR 0117): the person authorized the app, so the run acts with their permissions and approvals go to them, but the text comes from their AI, which may carry what it read elsewhere, so learning treats it as outside content (low trust, the agent's own memory, never a person's words for `remember`) and what the run posts is marked as relaying it. Text others wrote comes back only in `untrusted_text` fields, cleaned and capped, fenced in the text block between `BEGIN MESSAGE <nonce>` and `END MESSAGE <nonce>` with any marker inside broken, under a notice that it is content. Descriptions state facts in English, with no directive words (a test), every hint as a boolean, closed input schemas without root combinators and without `$schema`; errors are tool results with actionable words, unknown failures reported and generic. **Waits** (send's `wait_seconds`, `wait_for_reply`): at most 45 s, subscribed to the channel before reading, a check every 3 s, ended by the client's abort; the run is the message's, the one it was delivered to, or that agent's active one in the conversation; an unknown status is `failed`; a run waiting for its computer or parked on a provider outage is `still_running` (nobody has to answer it), `waiting_input` only for a wait on a person; 3 waits per person, 20 per workspace and 200 per process, past that `still_running` at once. No progress notifications in v1.

8. **Limits and audit.** Per grant 120 requests a minute and 5,000 a day (429, `Retry-After`, JSON-RPC `-32013`, never a challenge); sending 20 a minute and 500 a day per person and workspace; authorize 30 a minute per address; register 60 an hour per address and 2,000 successful an hour in all; token 30 failures a minute per address and 60 refreshes an hour per grant, never keyed on success by address or client (one CIMD id behind shared vendor egress is everyone's). Audit: `apps.connected`, `apps.scopes_changed`, `apps.disconnected`, `apps.token_created`, `apps.token_revoked` (a system actor with a reason when the server revoked), `apps.message_sent`. A personal token with no expiry needs a sign-in in the last 10 minutes (403 `reauth.sign_in`). `/mcp` refuses JSON-RPC batches (-32600; MCP dropped them in 2025-06-18) so one request is one call, and counts tool arguments (10,000 elements at most).

9. **Data** (migrations `0170_ai_apps.sql` and `0171_app_token_family.sql`): `oauth_app_clients` (global, the schema test's allowlist), `oauth_app_requests`, `app_grants`, `app_tokens`, `app_sends`, each of the last four with `org_id`. Hashed: codes and tokens, nothing else. Hourly cleanup: requests a day past their end, tokens 30 days after expiry or revocation, registrations with no connection 90 days after their last use (apps keep their `client_id` for good, and an abandoned sign-in never gets the `invalid_client` that makes them register again), sends after 90 days, grants unused for 90 days revoked. A password reset revokes every grant of the person; a removed member's grants are revoked there and at their next call; deleting an account or a workspace cascades.

10. **Network.** `/mcp` reads no cookies and checks no `Origin` (a DNS-rebound page holds no credential; Electron sends `Origin: null`). CORS `*` without credentials on `/mcp`, the discovery documents and token/register/revoke, with the MCP headers allowed and `WWW-Authenticate`, `Retry-After` exposed; `x-agentes-client` is never allowed, so the phone app's CSRF rule holds. `/mcp/` is the same endpoint. An envelope-less `initialize` is served without a modern `MCP-Protocol-Version` header (it negotiates from its body), and an Accept without `text/event-stream` gets both (every answer is JSON). Bodies on `/mcp` are capped at 128 KiB in the app, the compose file's Caddy and the nginx snippet. `serverInfo` lists a 512 px PNG icon, then the SVG. Behind Cloudflare these paths are never challenged (a WAF skip rule; on the free plan an IP Access allow for Claude's `160.79.104.0/21` and ChatGPT's ranges). Waits under 45 s fit Cloudflare's 100 s.

11. **Self-host parity.** On in every edition with no new environment variable; SELF_HOSTING.md says which apps need a public https address (claude.ai, the Claude apps and ChatGPT call from their servers) and which don't, and that an http-only LAN server uses a personal token. `bun run smoke --apps` checks the resource document and the exact challenge through the proxies in front.

12. **Rejected.** JWT access tokens (no gain with a per-call lookup, slower revocation). SSE in v1 (JSON is simpler behind every proxy; progress can come later for clients that send `progressToken`). A per-workspace switch for AI apps in v1 (default-allow; admins see and revoke everyone's connections, and every send is audited: an open question for the owner). `private_key_jwt` (added with Dinzo's assertion rules only if gate G3 fails). One connection for every workspace (a token would act across tenants; connect again from the other workspace).

13. **QA gates before beta**, on production with the operator's own account: G1 claude.ai Free and Pro, Claude Desktop, the phone; G2 Claude Code with and without `--scope user` (CIMD or DCR, its loopback); G3 ChatGPT custom MCP on Business and Pro (its card ships after); G4 the Cursor deep link and its three-address registration; G5 Codex login (listed after); G6 the VS Code deep link and MCP Inspector (CLI and browser).

## Consequences

- The person's own AI app becomes a front door to the workspace, with the same permissions they have in the chat, visible in the chat ("via Claude") and in the audit log.
- We own an authorization server. Its tests pin every edge case met in Dinzo, MillionSend and Real Oficial; changing it means changing them.
- Settings → Apps de IA (web and phone), the consent page and the via tag are the web and phone work on top of this API.

## Addendum (2026-11-02): tools that create, for imports from an AI app

Copying an export prompt into another app and pasting its reply back breaks on every app's own format. The person's AI app already knows its agents, instructions, skills and routines, and it can connect here: told "connect `PUBLIC_URL/mcp` and create here the equivalent of everything you have", it does the import itself.

1. **A third scope, `manage`.** Scopes are a ladder: `read` < `write` (sends tasks) < `manage` (creates and edits agents, routines and skills). A request's widest scope brings the ones below it (`parseScopes`); none asked is all three. The challenge and both metadata documents advertise `read write manage`. The consent page offers "Criar e editar agentes, rotinas e skills" only when the app asked for it, never pre-selected: clients ask for every advertised scope by default, so `write` stays the pre-selected access and the person opts into `manage` (the import card says to pick it), with its line under Pode; personal tokens can take it too. A connection made before keeps what it had: reconnecting with `manage` widens the grant (`apps.scopes_changed`, the "App conectado" email).

2. **The tools** (`packages/engine/src/apps/manage-tools.ts`, listed only with `manage`): `import_summary` (what exists, by name: agents, skills, routines, channels; roles and skill descriptions, which others wrote, come back as `untrusted_text`, fenced like the v1 read tools), `create_agent` (name, role, instructions, avatar color, optional handle; owned by the person, on the workspace's default AI, `NEW_AGENT_DEFAULTS`, which the person changes later), `update_agent_instructions`, `list_skills`, `create_skill` (a SKILL.md, or Markdown with name and description apart; optionally turned on for an agent), `create_routine` (agent, instructions, a schedule phrase read by the schedule reader, optional channel, else the person's DM with the agent: a routine a person asked for posts where they asked), `add_memory` (a fact or preference for an agent), `create_channel`. `list_channels` stays the v1 one. Each calls the engine function the web app calls (`createAgent`, `updateAgent`, `saveSkill`, `setAgentSkills`, `createRoutine`, `addContextItemByPerson`, `createChannel`), so every permission is the person's: a member without `create_agents` can't create an agent, without `manage_agents` can't install a skill or replace instructions, and only an agent's owner or an admin writes its memory.

3. **No duplicates.** An item with the same name (an agent's, case-insensitive; a skill's; a routine's for the same agent; a channel's) comes back as `existing: true`, unchanged: a skill is never overwritten by an import. Each create also takes an `idempotency_key`: the same key on the same connection within 7 days returns what it made, read from the `apps.created` audit row (`details.grantId`, `details.key`), so no table or migration. Two calls with one key at the same instant can both create; a unique row per key is the upgrade if that shows up.

4. **Audit, limits, telling the person.** Each creation is audited as the person, `apps.created` with the app's name (`details.client`), next to the engine's own row (`agent.created`, `routine.created`…); `update_agent_instructions` is `apps.updated`. Creations are limited to 30 a minute and 300 a day per person and workspace, across their apps, on top of the connection's own limits. Each creation tells the person in their inbox: `app_created`, one notice per connection that merges while unread and sums what was made (`latest.created`), read as "Claude criou 3 agentes e 2 rotinas pelo app", opening the newest agent, else the newest routine. Inbox only, no push.

5. **Memory sent through an app is outside content.** Text that comes through an app counts as outside content (ADR 0117), even under `manage`: the app wrote it, the person may never have read it. `add_memory` (`addContextItemByPerson` with `viaApp`) writes only the target agent's own memory (scope `agent`, never the team, the workspace or a person), with `app` evidence (`ref` the person) and no `human` evidence, so the item is high trust for that agent (its runs use it, labeled an unverified hint) but unverified: `isPromotable` never turns it into instructions or org context, and team sharing (`shareAcrossAgents`) and skills (`promoteHowTos`) take only lessons and how-tos, which `add_memory` never writes. The Memory tab shows it under Aprendizados as "Enviado por … por um app de IA" (`origin.by: app`), with Editar and Esquecer: a person's save adds `human` evidence and confirms it (a reworded save makes a new version, an unchanged one confirms the same item in place), Esquecer archives it. Still through the judge that refuses text changing permissions, audited and in the notice.

6. **The import UX.** The import step (web onboarding, Configurações › Importar e exportar, Criar agente › Trazer agentes; the phone's onboarding and import) gives each source app two ways in, side by side above its steps: "Conectar com MCP" and "Só o pedido" ("Por arquivo" for apps that hand back a file). MCP is the default wherever the app takes a remote MCP server and apps reach this server; ChatGPT dots offers it without defaulting to it (a dot reaching a custom plugin is undocumented, and custom MCP on some plans is read-only); Paperclip and an agentes.chat export have no MCP way. The MCP way shows that app's own steps (`IMPORT_APP_CLIENTS` in `packages/client/src/lib/app-clients.ts`), with "pick Criar e editar…" at the sign-in step, then the request to copy, then the person's agents created since the step opened, arriving live (the agents list, refreshed on `agents.changed`). It shows only where apps on the internet can reach the server (`serverPublic` on `GET …/apps`: https on a public DNS name that does not resolve to a private, loopback or link-local address, `reachableFromInternet`, resolved once per process with `publicHostAddress`; a failed lookup counts as public and is tried again); a self-hosted server on a private host shows the request way and one line saying why. Self-hosters with a public https name get it too.

## Addendum (2026-11-03): a guide for every major app, the QA gates as a note

"Conectar um app" listed Claude, Claude Code, Cursor and "Outro app" (VS Code, and Codex behind a gate). It now has a card with step-by-step instructions for 23 apps that support a remote MCP server, from each vendor's own docs as of 2026-11-03 (third-party guides where the vendor publishes none: Perplexity, Le Chat, the Gemini app's plans, Copilot CLI).

1. **Two groups, most used first.** Chat apps: ChatGPT, Claude, Gemini, Grok, Perplexity, Le Chat, Raycast. Editors and terminals: Claude Code, Cursor, Codex, VS Code, Gemini CLI, Devin Desktop (formerly Windsurf), JetBrains AI Assistant, GitHub Copilot in JetBrains, Xcode and Eclipse, Zed, Cline, Warp, Goose, OpenCode, Visual Studio, Continue, Copilot CLI. "Outro app" stays last, alone, as the generic fallback with the token button. VS Code and Codex leave "Outro app"'s tabs for cards of their own.
2. **One data file.** Each app's guide is data in `packages/client/src/lib/app-clients.ts`: its steps (shared words in `apps.dialog.step.*` with the vendor's own menu paths, buttons and fields as values, kept in its English), the address or a command/config with the address in it, deep links (Cursor, VS Code, Goose), and its notes (plans, who can add it). The vendor's names aren't translated: they are what the person sees in that app.
3. **Sign-in.** Every app signs in through this server's OAuth (DCR or CIMD, §4) except three: GitHub Copilot in JetBrains, Xcode and Eclipse, and Continue, whose docs show only a header for a remote server, and Warp, whose sign-in returns to `warp://mcp/oauth2callback`, a custom scheme §4 refuses. Their guides put `Bearer <token>` in the config and offer "Criar um token pessoal".
4. **The gates no longer hide or mark a card (changes §13's "its card ships after").** Every app is listed with its guide, verified on production or not, and no guide carries a note about it. Still unverified: ChatGPT (G3), Codex (G5), the Gemini app (its return address), Grok (sign-in not documented), Le Chat (said to skip DCR when the client secret is empty), Raycast (a `raycast://` return address would be refused by §4), JetBrains AI Assistant (whether it signs in at all), Perplexity and Copilot CLI (third-party docs only), Devin Desktop and Zed (their return address isn't documented; a custom scheme would be refused by §4) and Cline (its docs show OAuth only in the CLI). A gate that fails on production changes that app's guide, or removes its card.
5. **Left out.** Microsoft Copilot Studio (a business agent builder, and no official mark to draw), and the consumer Microsoft Copilot (no documented way to add a server).
6. **Marks.** Thirteen new official marks in `packages/ui/src/brand/marks.ts`, each with its source: Grok, Perplexity, Mistral (Le Chat), Raycast, Devin, JetBrains, GitHub Copilot, Zed, Cline, Warp, Goose, Visual Studio and Continue, all path marks, so the phone draws them too.

## Addendum (2026-11-06): changing what was imported

The second pass of a migration is changing what came over. `update_skill` (a skill's body and description, as a new version, through `updateSkill`) and `update_agent` (role, name and look, through `updateAgent` and `setAgentAppearance`) join `manage`, audited as `apps.updated` and limited like the creations. Every permission stays the person's, and `create_skill` still never overwrites.
