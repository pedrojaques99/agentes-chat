# 0056. Operator API and external provisioning

- Status: Accepted (2026-10-24). Amended 2026-10-25 by ADR 0065 (§10: the ready time and when the wait began, the ready email, no pairing with external provisioning, no approval step), 2026-10-26 (§10: a workspace on hold or suspended waits for no computer), 2026-10-27 by ADR 0079 (§4: limits and meters; §5: `platform_ai.threshold`; §8: billing holds, limits and the create refusal) and ADR 0076 (§5, §6: screened sessions), 2026-10-29 by ADR 0078 (the sign-up mode, the waiting list and early-access invitations), 2026-10-30 by ADR 0082 (§5: `agent.deleted`) and ADR 0088 (§4: a workspace's deletion and deletion hold; §5: the deletion's events; §8: a deletion is no standing; §9: the deletion hold; §10: a workspace being deleted waits for no computer), and 2026-10-31 by ADR 0089 (§5: `run.hop_limit`) and ADR 0103 (§4: the analytics reads), and 2026-11-02 by ADR 0127 (§4: the work analytics reads), and 2026-11-05 by ADR 0150 (§4: the Claude sign-in policy and the AI-accounts reads; §5: `account.failure` and a failed `run.finished`'s `failure`), and 2026-11-09 by ADR 0161 (§5: `machine.wake_wanted`; §10: the workspace's computer in standby, `busy` and `lastUsedAt`)
- Date: 2026-10-24
- Extends: ADR 0002 (nothing private runs in the server process), ADR 0004 (configuration), ADR 0025 (connected computers)

## Context

Whoever runs an instance for other people (agentes.chat Cloud is one) needs things the app's own API doesn't give: look up any workspace or account to answer a support or abuse case, hold or suspend a workspace, and give each workspace a computer prepared by an external provisioner the operator runs. ADR 0002 rules out a private module inside the server process, so those services run apart and talk to the server over the network.

The app API (`/api/app/*`) is the wrong door for them: it acts as one person (cookie session, CSRF), it changes freely between versions, and it sits on the public address.

## Decision

### 1. Its own listener, off by default

- `OPERATOR_API_TOKEN` (at least 32 characters) turns it on. Unset, nothing listens. Set, a second `Bun.serve` on `OPERATOR_API_PORT` (default 3001, same `HOST`) serves `/api/operator/v1/*` and nothing else (`apps/server/src/operator/app.ts`, started in `start.ts`).
- The public listener (`PORT`) never mounts it: `/api/operator/*` there is a 404, token or not.
- The port belongs to the operator's private network. The compose file doesn't publish it; a service on the same Docker network calls `http://agentes:3001`. It is never published nor put behind the public reverse proxy.

### 2. One bearer token

- Every request carries `Authorization: Bearer <OPERATOR_API_TOKEN>`, compared in constant time. Anything else is a 401, on every path under the prefix (unknown ones and the OpenAPI document too), so nothing about the API answers without it.
- No cookies and no CORS headers, so a web page can't call it on a visitor's behalf.
- The token reaches every workspace and account on the instance. It lives only in the server's environment and the caller's, is never logged (`secret: true` in the schema), and is rotated by hand.

### 3. A versioned contract

- The caller deploys apart from the server, so a server deploy must never break it silently. The version is in the path, `/api/operator/v1`.
- The OpenAPI document is served at `/api/operator/v1/openapi.json`, and a copy is committed in `apps/server/test/operator-openapi.json`. A test compares the two, so every change to the contract is a reviewed diff.
- Adding an endpoint or a field keeps `v1`. Renaming, removing or changing the meaning of one makes `v2`, served next to `v1` until the callers have moved.

### 5. The events feed: what happened, as metadata

`GET /events?after&limit` (up to 1000) answers `{ events: [{ id, at, type, orgId, userId, data }], next }`, oldest first. `userId` is the person the event is about or who acted. The server writes each event in the transaction of what it records (or right after a sign-in commits), in `operator_events` (`packages/engine/src/operator-events.ts`):

| Type | Written when | `data` |
| --- | --- | --- |
| `user.signed_up` | an account's first sign-in method is created | `email`, `method` (`email`, `google`, `github`, `apple`) |
| `session.created` | someone signs in | `ip`, `userAgent` (512 characters at most) |
| `user.deletion_requested` | a person deletes their account; `dueAt`: when it goes for good | `dueAt` |
| `user.deletion_canceled` | they restore it before that date | none |
| `user.deleted` | an account is deleted | none |
| `organization.created` | a workspace is created | `name`, `mode` (`team` or `personal`, ADR 0159) |
| `organization.deletion_requested` | an owner deletes a workspace, or its only member deletes their account, and it is read-only for 7 days (ADR 0088); `userId` is who asked | `dueAt`, `via` (`owner` or `account`) |
| `organization.deletion_canceled` | an owner restores a workspace being deleted; `userId` is that owner; `via: "account"` when it came back with its member's account | `via` when so |
| `organization.deleted` | a workspace's data is deleted, at the end of its deletion's 7 days (ADR 0088); `userId` is who asked, null once their account is gone | `requestedAt`, `via` |
| `invitation.created` | an invitation is sent or resent, or an invite link is made | `emailDomain`, `role`, `resent: true` when resent; `link: true` for a link |
| `agent.created` | an agent is created | `agentId` |
| `agent.deleted` | an agent is deleted for good (ADR 0082) | `agentId` |
| `mail.sent` | an agent sends, replies to or forwards an email | `agentId`, `runId`, `kind`, `recipients` (how many), `domains` |
| `run.finished` | an agent's run ends (done, failed or canceled) | `runId`, `agentId`, `brain`, `status`, `toolCalls`; a failed one `failure` (`code`, `cause`, ADR 0150 §5) |
| `account.failure` | a turn on a computer's AI account fails for a provider's or sign-in reason, at most once per account and cause every 10 minutes (ADR 0150 §5) | `accountId`, `machineId`, `kind`, `authMethod`, `cause`, `code`, `httpStatus`, `runnerVersion`, `protocol` |
| `machine.wake_wanted` | something wants the workspace's computer while it is in standby: a run (`run`), a person opening its view (`view`) or a request to it (`call`), at most once per computer every 10 seconds (ADR 0161) | `machineId`, `why` |
| `run.hop_limit` | the depth backstop (`AGENT_MAX_HOPS`) stopped an agent's hand-off: the per-stretch limits stop agents long before, so some path lost its stretch (ADR 0089) | `messageId`, `hop` |
| `task.finished` | a task on a computer ends (done, failed, canceled, or interrupted for good) | `taskId`, `agentId`, `executor`, `status` |
| `desktop_control.ended` | a screened segment of a person's control of an agent's screen ends, having read something (ADR 0076; only with `SESSION_SCREENING`); `userId` is who was in control | `agentId`, `segmentId`, `startedAt`, `endedAt`, `screens` (how many) |
| `content.viewed` | a review block is read (§6) | `ref` (`run:<id>`, `task:<id>` or `session:<id>`), `reason`, `operator` |
| `platform_ai.threshold` | a workspace's usage billed to the platform this UTC month first reaches 50%, and first reaches 100%, of its `platformUsdPerMonth` limit (ADR 0079) | `month`, `percent` (50 or 100), `spentUsd`, `limitUsd` |

- **Metadata only.** Ids, counts, domains and where a sign-in came from: never a message, prompt, subject, address list, file, credential or token. Content leaves only through §6.
- **Off by default.** Events are recorded only while the operator API is on (`OPERATOR_API_TOKEN` set); without it the table stays empty. `content.viewed` is always recorded, since a review block can't be read without the API.
- **No foreign keys.** An event outlives the workspace or account it names: that is when an abuse case needs it.
- **Paging never skips an event.** Ids and timestamps are taken before a transaction commits, so a slow transaction can commit an event that sorts before one already served. Each row keeps the id of the transaction that wrote it (`xid8`, from `pg_current_xact_id()`); the feed is ordered by it and serves only rows whose transaction is below `pg_snapshot_xmin(pg_current_snapshot())`, the point below which every transaction has ended. A row committed later always sorts after the cursor. The cost: a long transaction anywhere on the database holds the feed back until it ends; nothing is lost meanwhile.
- **`next`** is opaque. Pass it as `after`; an empty page returns the same value, so the caller polls with it until something new comes. Callers skip types they don't know: new types and fields keep `v1`.
- **After a restore from a dump.** `pg_dump`/`pg_restore` brings the rows but not the transaction counter, so the restored database numbers its transactions anew, below the restored rows. A cursor from before the restore is then past every id the database gave out: it is refused (400 `stale_cursor`) instead of waiting forever, and the caller starts again without `after`, skipping the event ids it has (they never change). The restored rows themselves would stay behind the commit horizon until the counter got there, so the server moves them to the front of the feed when it starts, before the operator API serves a page.
- **Kept 90 days** (pruned daily by the workers). The operator's services copy what they need and keep it under their own retention rules.

### 6. Review blocks: the only content

`GET /review/{run|task|session}/{id}?reason&operator` answers `{ kind, id, orgId, agentId, text }`: what one run or task did, or what was on an agent's screen while a person controlled it (a session, ADR 0076), for an abuse review (`packages/engine/src/operator-review.ts`).

- **Built by the server, never raw rows.** A run's block holds the message that started it, each tool call with its input and result, and the reply; a task's holds its title, the message behind it, its prompt, command, result, last lines of output and the files it touched; a session's, one screened segment of a person's control, holds the text of its first and latest screens, from the server's memory only, gone 10 minutes after the segment ends (a 404 then, and always on a server without `SESSION_SCREENING`). Plus a header of ids, brain or executor (or who was in control), status and times.
- **At most 12,000 bytes.** Every piece is cut first; when they still don't fit, the lowest-ranked go (tool calls before the request and the reply), and a last line says how many were left out.
- **Credentials masked** by their shapes (API keys, tokens, `Bearer` headers, `password=` and `token:` values, private keys) before anything is cut. Tool inputs are written as `key: value` lines so a field named like a secret is masked too.
- **Workspace text is quoted.** Everything people, agents, tools or web pages wrote is inside `<external_data>` envelopes, with any copy of the markers neutralised, so the reader (a person, or a model that judges it) weighs it as data and never follows it.
- **Every read leaves a trail.** `reason` and `operator` are required; a `content.viewed` event is written before the block is returned, in this server's database, where the operator's own services can't erase it.

### 7. Hooks are pulled, never pushed

The server never calls the operator's services. What it has for them waits in Postgres until they ask (the events feed above), and what they decide comes back through this API:

- standing: a workspace `active`, on `hold` or `suspended` (§8), an agent held, an account blocked; set here and enforced by the server at its existing choke points (model gateway, computer calls, permission checks, invitations, sign-in);
- external provisioning (`MACHINE_PROVISIONING=external`, §10): each workspace without a ready computer is a request the provisioner lists. It reports progress, and asks for a single-use enrollment code that the computer redeems through the device-code flow of ADR 0025, so the computer's own token never passes through the provisioner.

Nothing is lost while those services are down, and the server needs no delivery, retry or signing code. These endpoints join this API under the same token and the same contract test.

### 8. Workspace standing

`PUT /orgs/{orgId}/standing` with `{ state: active | hold | suspended, reason (64 characters at most), note? (2000), notice: shown | silent }` answers `{ state, reason, note, notice, changedAt }`. It is enforced where work starts, in `packages/engine/src/standing.ts`, never by a caller remembering to check:

- **`hold`: the agents stop.** The Model Gateway refuses every call. The machine hub refuses new work, and the bridge calls (`mcp.call`, `mcp.list`) of work already on a computer. A run that starts fails at once and says so, before any judge or model call, and leaves no new run for the messages it had taken. A routine's slot is skipped (`org_paused`) and the routine keeps its schedule. The router and the judge ask nothing: Jev bills the server, not the workspace. No invitation is sent, resent or accepted. People still read and write.
- **`suspended`: the workspace is closed.** All of the above, and every permission check (`requirePermission`, channel access) refuses with `org.suspended` (403). What its agents still have going stops each time it is set to `suspended` (so setting it again finishes a stop that failed halfway): every run not finished is canceled with the standing's text (a routine's run ends `org_suspended`) and hands its unread messages to no new run, and every live task is canceled on its computer (`task.cancel`; one the computer doesn't run, or that doesn't answer within 15 seconds, ends here and never resumes).
- Someone in a workspace that is suspended or on a hold, or whose account is blocked, can't create another one (`org.create_refused`), so the work doesn't carry on elsewhere. A billing hold (ADR 0079) refuses nobody, except the owner of a workspace waiting for its first plan (`payment`): `org.create_unpaid`, with that workspace's id.
- **Billing holds and limits** (ADR 0079). `PUT /orgs/{orgId}/billing-hold` with `{ hold: payment | unpaid | ended | null }` answers `{ applied, standing }`: a shown hold whose reason is that code, written like any standing here, and never over a hold set through `PUT …/standing` or a suspension (`applied: false`, as when it is already so). `PUT /orgs/{orgId}/limits` with `{ members, membersMax, payerUserId, storageBytes, uploadBytesPerDay, platformUsdPerMonth }`, each null for no limit (`membersMax`, the plan's top with seats added, and `payerUserId`, who pays for the plan, may be left out), answers them with `updatedAt`, which moves only when a value changes; limits and standing are independent.
- **A deletion is no standing** (ADR 0088, added 2026-10-30). A workspace an owner deleted is closed to changes and to all work (`org.deleting`, 403) for 7 days, its members still reading it (amended 2026-11-11), in columns of its own: setting a standing neither reads nor clears it, `standing` here, in `GET /me` and in `org.standing` never carries it, and `GET /orgs?standing=` filters by the standing alone. Past its date, a suspension or a hold that isn't billing's makes the deletion wait until it is lifted; a billing hold doesn't.
- **`shown`**: the workspace reads the reason ("This workspace is on hold: …", error `params.reason`), the change goes into its audit log (actor `system`), and a new state notifies its owners and admins (`org_standing`). **`silent`**: it reads only "Agents in this workspace are paused for review." or "This workspace is unavailable for now.", and gets no reason, audit row or notification: someone abusing it learns nothing about what was seen. Silent is only for when an authority's order forbids telling them. The note never leaves this API.
- Members hear `org.standing` (`state`, and `reason` when shown) on the workspace's realtime topic. Setting what is already set tells nobody again.
- Members also read it in `GET /api/app/me` (`organizations[].standing: { state, reason }`, the reason only when shown, never the note), so the apps know it before any refusal. On hold, the web app puts a line on top of the work area (the reason told, or only "Agents in this workspace are paused for review"); a run refused by the standing says so in the person's language (`run.org_paused` and its `reason`), not in the server's words. Suspended, the web and phone apps show a screen of their own instead of the workspace (why, when told; the person's other workspaces; sign out), with the socket still open so lifting it brings the workspace back at once. Both say where to ask about it: "Need help? Write to …" with the server's `SUPPORT_EMAIL`, else to ask the people who run the server.
- On agentes.chat Cloud (`isAgentesCloud(PUBLIC_URL)`) the standing in `GET /me`, `org.standing`, the refusals' `params` (`org.create_refused` too), a refused run's values and the owners' `org_standing` notice (`latest.cloud`) add `cloud: true`, and the apps follow a shown reason with how to contest it (legal@agentes.chat), in the inbox too. A shown standing whose reason is `review` reads as the automatic review hold's line, and `ended` (the hold of a workspace whose plan ended, a billing matter) reads as it is, with nothing to contest. A hold whose reason is `review.<category>` (`phishing_impersonation`, `account_takeover`, `fraud` or `illegal_content`) reads as the review line naming what was flagged, and a category the apps don't know as plain `review`. The standing's text (an error's message, a refused run's error) says a known category in words, never the code, and a run's values give the code back. The lines cite the Terms section they rest on by its number, and a test checks that number against the Terms this server serves. A self-hosted server's people read what they always read.
- Each process caches a workspace's standing for 5 seconds: a change applies at once in the process that made it and within 5 seconds in the others.
- What it doesn't stop: on `hold`, work already running on a computer (a background task, a computer brain's turn) goes on until its next model, computer or bridge call. The server never reaches a computer's network: cutting it off (on hold or suspended) is up to the operator's own controls on the computer, which the operator's service sets next to this call.

### 9. Agent hold, account block and deletion hold

- **`PUT /orgs/{orgId}/agents/{agentId}/hold`** with `{ held, reason? }` answers `{ held, heldAt, reason }` (`agents.operator_hold_at`, `operator_hold_reason`). A held agent gets the refusals of `hold` for itself only, with `agent.paused` (403): no model call, no new computer work or bridge call, a run of it fails at once ("This agent is paused for now.", `run.agent_paused`), its routines skip their slots (`agent_paused`), and the router never picks it, so the workspace's other agents answer instead. The workspace never reads the reason. Cached like the standing (5 seconds).
- **`PUT /users/{userId}/block`** with `{ blocked, reason? }` answers `{ blocked, blockedAt, reason, sessionsRevoked }` (`users.blocked_at`, `blocked_reason`, which Better Auth never reads, so they never reach a session or its cookie cache). Blocking deletes the account's sessions and phones (push devices), and Better Auth's `session.create.before` refuses it a new one (`ACCOUNT_BLOCKED`, 403, for every sign-in method). A signed session cookie keeps a browser signed in for up to 5 minutes without reading the sessions table, so the block doesn't wait for it: `getMembership` and `requireChannelAccess` read a blocked account as no member, so every permission check, channel and socket subscription refuses it on its next request, and its open sockets close at once (`membership.revoked` for each of its workspaces). It can't create a workspace, accept an invitation or delete the account (the workspaces where it is alone would go with it). Its memberships stay, so admins can still remove it or change its role, and unblocking gives everything back.
- `GET /users/{userId}` shows `blockedAt` and `blockedReason`.
- On agentes.chat Cloud the person reads the hold's or block's kind, never its reason, with how to contest it. A held agent's refusal and its runs' errors carry `{ kind, cloud: true }` (`network` when the reason starts with `network.`, else `operator`), and so does a blocked account's `ACCOUNT_BLOCKED` (`abuse` for `abuse.resignup`, `legal` for `legal_hold`, else `other`). Holding an agent there also notifies its responsible person and the workspace's owners and admins (`org_standing` with `latest: { statusTo: "agent_hold", holdKind }` and `source.agentId`). Held again for another kind, that notice closes and a new one says the kind its refusals now say. Letting it go closes it. No email is sent.
- **`PUT /orgs/{orgId}/deletion-hold`** with `{ held, reason? }` answers `{ held, heldAt, reason }` (`organizations.deletion_hold_at`, `deletion_hold_reason`), or 404 when there is no such workspace (ADR 0088, added 2026-10-30). It goes with a legal hold: while held, a workspace whose deletion was asked for, by an owner or with its only member's account, waits past its date instead of being deleted, closed, with everything in it. It refuses nothing and tells the workspace nothing (no audit row, no notice), restoring the workspace never lifts it, and once it is let go a deletion past its date goes ahead within an hour. `GET /orgs/{orgId}` shows it.

### 10. External provisioning: the workspace's own computer

`MACHINE_PROVISIONING=external` gives every workspace a computer from a provisioner the operator runs (`packages/engine/src/machine-provisioning.ts`, `apps/server/src/operator/machines.ts`). It needs `OPERATOR_API_TOKEN`: the server refuses to start without it, since nothing else would ever serve the requests. `off` (the default) changes nothing.

| Method, path | Answer |
| --- | --- |
| `GET /machine-requests?limit&cursor` | `{ requests: [{ orgId, orgName, createdAt, owner: { userId, email } \| null, provisioning }], next }`: every active workspace not being deleted whose computer isn't ready, oldest first, in keyset pages of up to 200. `owner` is its first owner; `provisioning` what the provisioner last said (null before anything). Empty with `off` |
| `PUT /orgs/{orgId}/provisioning` | `{ state: preparing \| waiting \| problem, step?, stage?, reason?, expectedReadyAt?, specs? }` → 204; 409 `provisioning.ready` once the computer is ready; 403 `org.paused` / `org.suspended` / `org.deleting` unless the workspace is active and not being deleted. An older client's `etaSeconds` reads as that many seconds from now |
| `POST /orgs/{orgId}/machines` | `{ name? }` → `{ machineId, enrollCode, expiresAt }`; 403 `org.paused` / `org.suspended` / `org.deleting` unless the workspace is active and not being deleted |
| `GET /orgs/{orgId}/machines` | `{ machines: [{ id, kind, managed, name, online, lastSeenAt, runnerVersion, protocol, standby, busy, lastUsedAt }] }`: every computer still in the workspace; `standby`, `busy` and `lastUsedAt` are the workspace's own computer's (ADR 0161), false, false and null for the others |
| `PUT /orgs/{orgId}/machines/{machineId}/standby` | `{ standby }` → `{ standby }`: the workspace's computer is asleep by the operator's doing, or no longer (ADR 0161); 404 when the workspace has no such managed computer |
| `DELETE /orgs/{orgId}/machines/{machineId}` | 204; 404 when the workspace has no such managed computer (also once removed) |

- **A request is a workspace, not a row.** Nothing is queued: an active workspace whose computer isn't `ready` is listed until it is. One on hold or suspended is never listed, so a workspace whose computer was retired for abuse doesn't get another one; holding it is the provisioner's way to stop. Such a workspace waits for no computer (added 2026-10-26: the rows stayed, so a workspace ended before it got one read "waiting" for good): setting it on hold or suspended drops what the provisioner last said of its computer, in the transaction that sets it, every time it is set; a ready computer stays ready. A report reads the standing under a share lock on the workspace's row, which setting it waits for, so a report sent as it is held is either refused or dropped, never left behind; removing its computer reads it the same way and starts no wait. Its people are told of no wait: while it isn't active and its computer isn't ready, `computer-setup` and `machine.provisioning` say `state: null` and nothing of a wait (no step, time or size), and the apps ask for it again on `org.standing`. Active again, it is a request like any other. A workspace being deleted (ADR 0088) is no request either (added 2026-10-30): deleting it drops a wait that isn't ready, reports and codes for it are refused (`org.deleting`), removing its computer starts no wait, its people are told of none, and no ready email goes out. Restored, it is a request again. The provisioner reads its deletion in the events feed (§5).
- **One managed computer per workspace.** `machines.kind` is `connected` (a person paired it), `host` (the server's own) or `managed`. A unique index on `org_id` where `kind = 'managed'` (removed rows included) keeps one row: the first `POST` makes it (paired by nobody, no token yet), every later one reuses it, and one removed comes back. Unless `name` is given, it is named the way the apps call it, "Acme's computer" ("Computador da Acme"), in its first owner's language: a name like any computer's, so every message that names it says a computer, never the bare workspace. Renaming the workspace renames it too while it still has that name; a name someone gave it stays.
- **The code.** Each `POST` writes a confirmed `machine_device_codes` row for that computer (single use, 10 minutes, stored as SHA-256) and returns it once as `enrollCode`; an earlier code for it still unused is denied, so at most one works. The computer redeems it at `POST /api/machines/device/token`, the same poll as a code a person confirmed; the `machine.paired` audit row has actor `system`. The code names the computer as its own `previous_machine_id`, the reconnect case of the device-code flow, so one that expires unused never removes the row. A person's computer can never come back as the managed one through a reconnect code.
- **The computer's side.** `agentes-runner pair --server <url> --enroll-file <file>` (or the installer's `--enroll-file`, which connects even a home connected before) reads the code from a file, removes the file at once, whatever happens next, and polls with the code; nobody confirms anything. The code never goes on a command line, which other local users can read, nor into the runner's config or output. A file that doesn't hold something shaped like a code is refused before anything is sent. The config is written as for any pairing, in whatever home the runner uses.
- **Progress.** `preparing` (`step`: `reserving`, `starting`, `installing`, `connecting`), `waiting` (`reason`: `capacity`; an older client's `approval` reads as capacity, as do rows it wrote) and `problem` are the provisioner's; `ready` is the server's (`machine_provisioning.state`). `step`, `stage` and `expectedReadyAt` are kept only with `preparing`, `reason` only with `waiting`; `stage` is what the computer is doing within its step (`ordering`, `wiping`, `starting`, `booting`, `updating`, `restarting`, `network`, `firewall`, `apps`, `connecting`), any word of up to 64 characters being kept, so the provisioner can add one before the apps have words for it (they say its step meanwhile); `specs` (`{ cpus, memoryGb, diskGb }`) stay until replaced; `since` restarts only when the state, step or reason change. One wait (`preparing`, until ready, another state, a removal or a hold) counts down to the earliest ready time it was told: a later one is kept out, and a report without one keeps it, so a part running past its time, whose ready time moves later with the clock, reads as running over, never as a countdown that comes back up (ADR 0065 §3). Members hear `machine.provisioning` (the fields of `computer-setup` but `mode`) when something they see changes. Once `ready`, `PUT` is refused until the computer is removed, so a late write can't take a working computer back to "preparing".
- **When the wait began.** `requested_at` is written only when the computer is taken away and kept by every later report; null reads as the workspace's creation, so making a workspace writes nothing. A report that leaves the wait's ready time over a minute ahead, `waiting` or `problem` sets `email_when_ready`: the owners were told they'd get an email.
- **Ready on the first hello.** The managed computer's first hello since it was issued sets `ready` (a conditional write: only the transition counts), gives the computer to every agent of the workspace that has none, tells the members (`machine.provisioning`, `agent.computer`) and notifies the owners (`computer_ready`, in the app and on their phones). After a long wait (`email_when_ready`, or more than a minute since `requested_at`) a server that sends email emails them too, once, in their language, with the next steps, queued in the same transaction as the ready and only while the workspace is active (ADR 0065 §4). A reconnect changes nothing, so an agent someone moved off it stays where they put it. Agents created later start on the workspace's managed computer (or the server's own) once it has connected; the agent owner may put their agent back on it, though nobody paired it.
- **Removal.** `DELETE`, before the provisioner wipes or retires the computer, does what removing any computer does (its token stops working, its connection closes, its agents are left with no computer) and also denies its unused codes and starts the wait over (a `preparing` row with `requested_at` now), so an active workspace is a request again; one held or suspended is left with no wait. People can't remove the managed computer (`machine.managed`, 403) nor turn its tools off or take a folder away (`machine.managed_access`, 403): only the computer itself could undo that, and nobody in the workspace reaches it. Admins may still rename it.
- **What people see.** `GET /api/app/organizations/{orgId}/computer-setup` (every member) answers `{ mode: external | pair, state, step, stage, reason, since, requestedAt, expectedReadyAt, secondsLeft, secondsWaited, specs, notifyByEmail, machineId }` (all null but `mode`, and `notifyByEmail` false, with `pair`; `preparing` with nothing reported yet; `state` null and nothing of a wait while the workspace isn't active and its computer isn't ready). `secondsLeft` and `secondsWaited` (since `requestedAt`) are counted by the server when it answers; `notifyByEmail` says the server sends email. The computers list shows the managed one with `kind: managed` and no hostname, OS, arch or workspace folder; the offline computers and their targets (`…/machines/outages`) mark it `managed: true`, its platform `other`. An agent with no computer while its workspace's is still being prepared is told that (`computer_status`, its tools' descriptions) instead of "no computer".
- **The apps** (`setupView` in `packages/client/src/lib/computer.ts`, live from `machine.provisioning`) say where it is in plain words: the step ("Turning it on", 2 of 4), or the stage within it when they have words for it ("Updating the system", still 3 of 4), waiting (in line: no computer on its way yet), a problem, ready, or paused (`state: null`: on hold, nothing on its way, no notice, and the pickers offer it no more than when it is ready). Never a system, an address, a provider or a tool list: its size ("4 CPUs · 8 GB of memory · 100 GB of disk") and one user per agent are what it is. Until it is ready: a notice on top of the work area naming the agents that wait for it; the onboarding's computer step shows its progress instead of a choice, and the person goes on; Settings → Computers shows its card in place of the cloud computer's; an agent with no computer reads as waiting for it, and pickers offer it in place of "no computer", as the computer it will be (moving an agent there keeps its brain). Once ready, its card shows online or not and its agents, and on a server without the cloud computer the pickers no longer offer the cloud: an agent with no computer reads "No computer". Its page never offers Remove, the folder it was connected from or turning anything off; when its browser or the agents' desktops don't work, it says so and where to ask, never a runner's reason or command. It is drawn as a server before and after it exists, never as the cloud computer an agent may get of its own.

## Consequences

- A self-hosted instance gets no new surface unless its admin sets the token; with it, the same API serves their own automation.
- One token holds every operator power. Splitting it (read-only, per caller) waits for a second caller.
- Answers carry personal data (names, emails, IP addresses), and with the token set the server keeps 90 days of events about people who may have deleted their account since. Callers keep what they copy under their own retention rules.
- The feed can lag behind by as long as the longest transaction running on the database.
- A change to the contract fails the test until the committed document is regenerated (`UPDATE_OPERATOR_OPENAPI=1` on `apps/server/test/operator.test.ts`), so it is always a deliberate diff.
- With external provisioning a workspace waits for its computer as long as the provisioner takes: nothing in the server times out or falls back to pairing, and its people can't connect computers of their own (`machine.pairing_off`, ADR 0065 §5); the server refuses to start with `HOST_COMPUTER_TOKEN` too.
