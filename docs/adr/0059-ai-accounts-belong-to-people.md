## Context

ADR 0041 put Claude and ChatGPT subscriptions on a connected computer, one folder per account, managed only by the person who paired the computer. Three things changed:

- **Computers without a person.** A Cloud workspace's machine and a self-hosted server's own computer have no pairer, yet every member wants to bring their own plan to them.
- **Several seats per person.** A team plan gives one person several seats. With labels such as "Claude Max · Max" nobody could tell the rows apart, or whose account served which agent.
- **Sharing a personal plan.** ADR 0032 warned once, when a plan brain was chosen, and after that the agent answered whoever its audience allowed, on one person's subscription.

People also asked for more providers than Anthropic and OpenAI (DeepSeek, Kimi, Z.ai's GLM, MiniMax, OpenCode), for the providers' official logos wherever a provider is named, and for each plan's usage limits on screen.

## Decision

### 1. An account belongs to the person who added it

- The owner is bound when the sign-in **starts** (the row is written then, with the caller as owner), never inferred later from who polled first. Only the person who started a sign-in may send its code, check it or cancel it.
- Accounts the desktop app reports with no sign-in started from the web belong to the computer's pairer. On a computer with no pairer they have no owner: nobody assigns them, and the pairer or an admin can remove them.
- Only the owner sees the account's email, renames it, assigns it or signs in to it again. The computer's pairer can disconnect any account on that computer; on a computer with no pairer, so can admins.
- **Who adds:** any member on a computer with no pairer (the Cloud machine, the server's own computer). On a personal computer only its pairer adds accounts, as before: other people's sign-ins on someone's laptop raise a consent problem, and they would outlive the computer if its token were revoked.
- A person who leaves the organization or deletes their account has their accounts signed out and removed from every computer, with a tombstone until the runner confirms. They are never inherited by anyone.

*Amended 2026-10-30 (ADR 0088):* a deleted workspace's accounts leave its computers before it goes. At its purge every account on them becomes a tombstone, and the purge waits up to 60 seconds for its online computers whose runner removes accounts to sign them out. An offline computer keeps them, and its token dies with the workspace. A deleted account's tombstones are announced to the computers of every workspace it was in, those that close with it included. A person who leaves also takes the computers they connected there, unless in system mode (ADR 0088 §11).

### 2. One account thinks for one agent

- An account serves at most one agent (a unique index). Picking an account another agent uses offers to move it here.
- The computer's own sign-in (no folder) can still serve several of its pairer's agents.
- Each seat's limits stay predictable, and on a computer where every agent runs as its own OS user, one sign-in folder can't be shared anyway.

*Amended 2026-10-27:* one login (a row and its folder) still serves at most one agent, and an account may have one login per agent where `LOGIN_PER_AGENT` (`packages/providers/src/plans.ts`) allows it. "All agents" then signs each agent in with the same account, back to back, and a coding plan's key is pasted once and sealed to each login. The coding plans allow it now: a key has no refresh token, so its copies never sign each other out, and several agents of one person are still one user of the plan. Claude's and ChatGPT's sign-ins stay one agent per account until several sign-ins of one account are seen to hold through their refreshes. Users report that a new Claude sign-in can sign the account's other sign-ins out (anthropics/claude-code #20310, #40419, #80292), and OpenAI documents one `auth.json` per runner or serialized job stream. Each turns on by flipping its value.

The plan's panel says whom it is for ("For [All agents ▾]"). "All agents" means the person's agents with no AI on one computer, and those already on that plan. An agent on the API key stays out, since a plan would make it answer only its owner, and one on another plan keeps it. The setup opens on "All agents" where the plan allows it. Elsewhere the panel opens on the agent it was opened for, else on "All agents" while two or more have no AI, else on the first with no AI. One key fanned out to many agents counts each login against the ten sign-ins a person starts per computer every 15 minutes.

*Amended 2026-10-30:* Claude's sign-ins are one login per agent too (`LOGIN_PER_AGENT.claude_code`), so one Claude account thinks for several of its owner's agents. Signing in for an agent with an account another agent uses gives that agent a login of its own under the account's name: in Connect an AI for one agent, in the setup's AI step and with "All agents" (one sign-in per agent, back to back, the first one's email the next ones' hint), and from the agent's page, which offers such an account as one more login for this agent ("Also used by Ada") instead of moving it. A new sign-in of an account its owner already has on that computer is no longer refused for Claude; §6's refusal now holds for ChatGPT, which stays one agent per account. Signing in again as another account is still refused for both. Renaming one login renames them all, and removing one leaves the others thinking for their agents.

What to watch for: users report that a new Claude sign-in or a token refresh can sign the account's other sign-ins out (the issues above). A login signed out this way finds out at its next turn, when Claude's endpoint refuses it. The runner then marks it refused, and it reads as signed out whatever the CLI's own status says, until a sign-in there succeeds. The agent says its AI is signed out (its no-AI card, `not_signed_in`), and its page and Settings › AI accounts offer Sign in again for that login. No other login stands in by itself. If logins keep signing each other out, signing one in again may sign another out.

The fallback is setting `LOGIN_PER_AGENT.claude_code` back to false: a new sign-in of an account already on that computer is refused again, as before, and the logins made meanwhile keep thinking, each for its agent, until they are removed. On a computer the person connected, the computer's own sign-in still thinks for all of their agents there.

*Amended 2026-11-02:* every plan is one login per agent (`LOGIN_PER_AGENT`: ChatGPT's and Cursor's too), so any account thinks for any of its owner's agents: the same account again is one more login under its name, never refused as a duplicate (§6's refusal no longer applies to any kind). A login signed out by another's refresh reads as signed out at its next turn, as Claude's. The beta labels on ChatGPT and Cursor ("Em teste") are gone, and so is the API's `experimental` flag on brain options.

*Amended 2026-10-30, later the same day: one sign-in for all of its owner's agents.* From runner protocol 29 on (`SHARED_ACCOUNTS_PROTOCOL`), an account signed in once on a computer thinks for every agent its owner gives it there, with no other sign-in, and so does one coding plan key. Each agent keeps its own OS user for everything else, the account's credential never reaches our server, and no agent that doesn't think with the account can read it. The runner says which accounts do (`shared`, kept in `machine_accounts.shared`); any other login still thinks for one agent, with one login per agent where `LOGIN_PER_AGENT` allows it, under a lock on its row now that no unique index holds it.

- Where every agent is the runner's own user (a person's own computer), any account folder thinks for all of its owner's agents there, as the computer's own sign-in always has: Claude Code and Codex keep one sign-in for several processes of one user, each taking a lock and reading its file again before it refreshes.
- Where each agent is its own OS user (`install.sh --system`: the Cloud, a server's own computer), a sign-in made for all agents (the server asks for it, `begin` with `shared`) stays in its account folder, root's alone (700, never lent, `<id>.shared` beside it). Root hands each turn what its CLI needs over the agent's worker link (`AccountManager.grant`), never in a file the agent can reach, and the CLI runs in a folder of that agent's own for the account (its sessions and settings, no sign-in).
  - Claude: root signs in with `claude setup-token` instead of `claude auth login`, with the same link and sealed code (§6). That command draws its screen only in a terminal, so it runs in one of its own, and its link and token are read off the screen it draws, never off its bytes. It makes a one-year token that only makes model requests on the person's plan; Claude Code never refreshes it (a refused one is kept, not swapped for another sign-in), so the agents' turns never sign each other out. Root keeps it in `token.json` (600). Each turn's Claude Code gets it on a descriptor of its own, never in an environment (security, below), with Anthropic's endpoint, no other cloud and the runner's proxies pinned in the runner's own `--settings`, as for any account. The token says neither the email nor the plan, so the account is named "Claude" until its owner renames it, and its usage comes only from its turns (§7): without the profile scope, the usage request has no limits to say.
  - A coding plan: root keeps the key in `provider.json` and hands it to each turn the same way; the turn's CLI gets it in its environment, as a key always has.
  - ChatGPT (amended 2026-11-02, runner protocol 38, `SHARED_CODEX_PROTOCOL`): a sign-in there is made for all agents too. Root runs `codex login --device-auth` in the account folder and keeps its `auth.json` (600, never lent). Each turn, route and Codex task gets root's newest copy with it (`codex_auth` grant), written into the agent's own folder for the account unless the copy there is newer and of the same ChatGPT account. While it runs, the worker watches that copy and sends each refreshed one back (`codex.auth`, taken only from a worker root handed that account), and root keeps it when it is newer and signs in to the same ChatGPT account. Copies used at once are fine until one is due for its refresh (8 days, Codex's `TOKEN_REFRESH_INTERVAL`), which rotates the refresh token: the first turn then takes it alone and the others wait up to a minute for its refreshed copy, as OpenAI's one `auth.json` per serialized job stream asks (learn.chatgpt.com/docs/auth/ci-cd-auth). Older runners keep lending it to one agent.
  - Gemini (amended 2026-11-11, runner protocol 58, `SHARED_GEMINI_PROTOCOL`; details in ADR 0143 §4): a sign-in there is made for all agents too. Root runs `agy acp --login` in the account folder and keeps the CLI's sign-in file (never lent), after trying a copy of it in an empty home first. Each turn gets a copy (`agy_auth` grant), written into the agent's own folder for the account while that agent's turns run and removed after the last (a worker killed mid-turn leaves it until that agent's next worker starts). Google's refreshes don't rotate the refresh token, so nothing comes back to root.
  - A turn's plan usage now reaches root from the agent's worker (`usage`, taken only for the account a turn in flight thinks with). Before, it stayed in the worker.
- A folder that was ever lent to an agent's user stays that agent's alone, since its files were that user's to write. Its next sign-in, or a new key, makes it one for all agents, in place: root takes it back and empties it first, and its agents keep it.
- An account the runner stops calling shared (signed in again for one agent once the switch below is off, or a runner before protocol 29) thinks for one agent again: if more than one thinks with it, they all let it go and their owner picks again, so one login never serves two users' processes.
- The apps:
  - Connect an AI offers first the accounts of that plan its owner already has there for all agents ("Use Claude Max", "Also used by Ada"), then another account, and "All agents" signs in once and gives the account to each in turn ("One sign-in for all of them.").
  - The agent's page offers such an account as it is, "Also used by Ada", with nothing to sign in and nothing moved.
  - AI accounts shows every agent that thinks with an account and gives one made for all agents to one more ("Use for Mila too"), never to an agent on the workspace's API key (a plan would make it answer only its owner: that move is its own page's). At a plan's limit the agent's page offers such an account too.
  - Disconnecting an account, and a sign-in that ends, act for all of its agents at once; Sign in again (or New key) is once for all, and until it is done the agents keep thinking with what the account has, unless that was refused.
  - A new sign-in for all agents of an account its owner already has there for all agents is refused (§6), with that account to use instead. One made for one agent leaves room for it, since it can't think for the others. Signing in again never turns a login into another's duplicate: it keeps its agents, and so the logins made one per agent before keep working, each for its agent, also where every agent is the runner's own user and the runner calls them all shared. A token says no email, so a second token sign-in of the same Claude account can't be told apart and is kept as another account, and signing in again can't tell that another account came back (the account keeps the email and plan it had).
- Security: root reads the token, the key or the folder, and the worker of each agent that thinks with the account gets it for that agent's turns. A token never sits in an environment, where any process of that agent's user could read it (`/proc/<pid>/environ` needs no `ptrace`) and every command its CLI starts would inherit it: Claude Code reads it on descriptor 3 at its start (`CLAUDE_CODE_OAUTH_TOKEN_FILE_DESCRIPTOR`), then closes the descriptor and drops the variable, the way Claude Code's own runner hands a code review its tokens, "on file descriptors 4 and 5 instead of in its environment" (its own message, 2.1.314). Checked with Claude Code 2.1.296 to 2.1.314 against a local endpoint: the token went out as the bearer, and a command it ran saw neither the token nor the descriptor, nor did the CLI's own environment hold it. The variable isn't among Claude Code's documented ones (code.claude.com/docs/en/env-vars, read 2026-10-30): a release that stopped reading it would find no sign-in in the agent's folder, so its turn would fail as signed out, never think with anything else. A key still goes in its CLI's environment, as before. Either is redacted from everything the runner sends, streamed text included (a batch keeps back what could start one). What that agent's commands could still reach is its CLI's memory, where `ptrace` is open within one user (ADR 0062), as they could that agent's own sign-in before. Root tells each agent's worker which account its agent thinks with now (`worker.state.account`, at each agents frame and when an account goes), and the worker closes its processes on any other account, a busy one once its turn ends (`BrainManager.keepAccount`): seconds after the change, none of that agent's processes keeps a credential it no longer thinks with. Admins may open its terminal again from the change itself, so those seconds are the window left. No other agent can reach it: each is another OS user, and the folder is root's alone. While an agent thinks with its owner's plan, only its owner controls its desktop or opens its terminal (§8, unchanged), since a shell as that user reaches its processes. A token makes model requests on its owner's plan and limits and reaches nothing else of the account (no profile, Remote Control or claude.ai connectors), from anywhere, until it is revoked or a year passes.
- Revoking: a token ends in Claude's settings, where each shows only as a Claude Code connection, or after a year; the CLI can't end one. Disconnecting deletes it from the computer, the workers close the processes that had it, and the dialog says to revoke it on Claude too. The first turn after a token is revoked or has expired is refused: it ends at once as signed out (Claude Code would retry for minutes), and the account reads as signed out for all of its agents until it signs in again, once.
- Terms: Anthropic says developers "may not collect, store, or intermediate Claude.ai credentials or session tokens", that "sign-in to a Claude account must complete through Anthropic's own flow", and that this doesn't prevent "an end user from signing in to the unmodified Claude Code binary with their own Claude subscription, including where a platform hosts Claude Code" (code.claude.com/docs/en/legal-and-compliance, read 2026-10-30). The sign-in still completes in Claude Code, through Anthropic's flow, and the binary is unmodified. Anthropic documents `claude setup-token` for "CI pipelines, scripts, or other environments where interactive browser login isn't available": the CLI prints the token for its person to set "wherever you want to authenticate" (code.claude.com/docs/en/authentication), and its own `/install-github-app` keeps one as a repository secret (code.claude.com/docs/en/github-actions). The runner keeps it as such a store does: on that person's computer or their workspace's, for the unmodified CLI of their own agents on their own plan; our server never holds, routes or sees it. A plan still thinks only for its owner's agents (§3) and answers only its owner until they turn on "Replies to everyone" (§5). Anthropic may still read the runner as a developer storing a credential, most of all on the Cloud, where we run the computer; ADR 0041 and this ADR rejected keeping the token for that reason, and Anthropic invites questions about permitted authentication methods. The risk is taken here, and the switch below takes it back.
- The fallback: setting `SHARED_SIGN_INS.claude_code` (or `key`, `packages/providers/src/plans.ts`) to false makes new sign-ins of that kind one per agent again where each agent is its own OS user. Accounts made for all agents keep thinking until they are signed in again (then for one agent, as above) or removed.

### 3. A plan only serves its owner's agents

A personal plan thinks only for agents owned by the plan's owner. This is checked when an account is chosen, when an agent changes owner (the plan is cleared), when an account goes away (the agent goes back to the API, or waits with no AI), and at run time (`plan_not_owner`, which also covers an owner who left). Runs never slip onto someone else's plan.

*Amended 2026-10-30:* on a computer nobody connected (the Cloud workspace's; the server's own computer is its owner's) the computer's own sign-in is nobody's plan, so it never thinks for an agent there. Such an agent's run reads it as not signed in (`not_logged_in`, ADR 0041 §1) instead of `plan_not_owner`: it fails at once with no AI and Connect, rather than waiting for a computer whose coming back would change nothing.

*Amended 2026-10-31 by ADR 0041 §5.1:* a background task's Claude Code or Codex is checked the same way when it starts. Before, a task ran on the computer's own sign-in for any agent; now one that would think with someone else's plan, or with nothing on a computer nobody connected, doesn't start, and its agent reads why.

*Amended 2026-11-03:* who picks the account is no longer the agent's owner alone. A plan still thinks only for its owner's agents, so the choice is still among the agent's owner's accounts on its computer (and the computer's own sign-in where they connected it), but an admin (`manage_agents`) picks among them too, moves the agent off them onto another of the owner's plans or the API, and may take a login from another of the owner's agents ("Mover para cá"). Signing an account in, renaming it and its paid extra usage stay its owner's. An admin's own plan still never thinks for someone else's agent: for that the agent becomes theirs first. "Só Walter troca" gives way to a plain line under Conta for the admin, "Só contas de Walter, responsável pela Ada: um plano só pensa pelos agentes do seu dono.", on the web and the phone; "Usar em outros agentes" follows the same rule (`account_owner` when the account's owner isn't the agent's).

*Amended 2026-11-04:* an admin couldn't give an agent, the team's right hand included, a plan a teammate had already connected to the workspace. A role key now allows it: "Usar planos de outras pessoas" (`use_others_plans`, in the tools area of ADR 0085), held by the administrator roles and the workspace's owners, never by `everyone`, so no migration backfills it. Whoever holds it sees every plan on the agent's computer, each with its owner's name and what it is (its plan, its email only to its owner, as in §4), in Connect an AI's "already connected" rows and on the agent's page, on the web and the phone (`canUseOthersPlans` in the brain view), and may give one to any agent they may manage (`manage_agents`, or their own agent), Lodi included. A login another agent thinks with stays there (`account.in_use`, even with `moveAccount`): only its owner moves it; one made for all of its owner's agents (§2) thinks for this one too. The server checks it in `setAgentBrain`, where every account is set (`nextBrainAccount`; for the right hand, giving it someone else's plan). The agent stores who gave it (`agents.brain_account_lent_by`, migration `0213_plans_lent`, set whenever the account changes), and a plan thinks for another person's agent only while that is set (`planIsOwners`: the plan's owner still in the workspace is enough then). The plan stays its owner's: its usage is recorded on its account as before, only its owner turns its paid extra usage on (`brain.extra_owner_only`, off when it is given), the agent starts on its own owner alone as onto any plan (§5), and when someone else lets more people talk to it, the email goes to the plan's owner (`agent.plan_opened`). Giving it is audited (`account.lent`) and queues `agent.plan_lent`: the plan's owner gets one email in their language ("Carlos conectou o seu plano do Claude ao agente Ada", `plan_lent`) and an inbox note (`plan_lent`) with "Tirar de volta" (that agent) and "Tirar de todos os agentes" (every agent someone else gave it to), `POST …/ai-accounts/{id}/take-back`, the plan's owner only. Taken back, each agent goes back as when an account goes (`releaseAgents`), audited (`account.taken_back`), and the note is done. Changing an agent's owner still clears a plan the new owner doesn't own. Plans on another computer than the agent's aren't offered: the agent moves there first. The phone opens Contas de IA from the note; taking back is on the web's inbox.

### 4. Labels people recognize

Automatic names are the maker and the plan, numbered per owner: "Claude Max", "Claude Team 2", "ChatGPT Plus", "GLM Coding", "Kimi Code", "MiniMax", "OpenCode Go". The owner sees the email under the name (and the organization of a team seat); everyone else sees "Claude Team 2 · {owner}'s" and never the email. The same email twice for one owner on one computer is refused, and the new folder is removed.

*Amended 2026-10-27:* where the account may have one login per agent (§2), the same account again is another login: it takes the account's name, and renaming one renames them all. Logins of one account are told apart by its email (in any case) or its key's last 4, never by the name, which any rename can repeat, and the apps show them as one row.

*Amended 2026-10-30:* an automatic name leaves the plan out: "Claude", "ChatGPT" or the coding plan's name, numbered per owner ("Claude 2"). The apps show the plan once, beside the name ("Claude · Max"), from what the computer last said, so an upgrade or a renamed plan never leaves a name that says another plan; a computer's own sign-in reads the same way by its maker ("Claude · Max"), and a name that already says its plan (as servers before this amendment name accounts, which the phone still meets) isn't followed by it again. Anthropic renamed its plans that day: Max 5x is Max and Max 20x is Ultra (claude.com/pricing). Claude Code's `auth status` says `max` for both, so the runner tells Ultra apart by the organization's rate-limit tier that the CLI writes at sign-in into the account folder's `.claude.json` (`default_claude_max_20x`); where the CLI couldn't fetch it, an Ultra reads as Max. A folder that was lent to an agent's user (system mode) never runs a CLI as root again, so its plan comes from that file alone (the organization's type and tier, one of the plans' words whatever that user wrote there), and an Ultra stored as Max before the rename becomes Ultra at the next look, with no new sign-in. Automatic names given before ("Claude Max", "Claude Team 2") became "Claude", numbered per owner, oldest first (the `claude_account_names` migration); a name someone chose stays.

### 5. "Only replies to you"

- An agent that thinks with a personal plan answers only its owner by default: the audience is `owner`, enforced everywhere a person's message can start a run (ADR 0032's audience gate).
- Turning the switch off shows the provider's own words about personal use and that answering others might go against its terms. Accepting sets the audience to everyone and is audited with the date. Choosing a plan no longer asks anything; only sharing it does.
- Only the plan's owner can widen the audience of an agent that thinks with their plan. Admins can only narrow it.
- With sharing on, anyone who can talk to the agent can make it use the owner's plan and, on a computer where agents share one OS user, reach its sign-in.
- A plan also picks who answers its owner's own messages nobody mentioned, only on a self-hosted server, and never for anyone else's (ADR 0074 §3).

*Amended 2026-10-27:* where the server provisions the workspaces' computers (`MACHINE_PROVISIONING=external`, the Cloud), the service runs the plans' CLIs for its customers, and the providers' conditions for platforms that do want each person on their own plan ("Each end user must authenticate with their own Anthropic API key, Claude subscription plan credentials, or 3P inference provider credential", code.claude.com/docs/en/legal-and-compliance). There an agent on a plan answers only its owner whatever its stored audience, and nobody can widen it (`plan.personal`). An agent shared before narrows, and answers its stored audience again once it moves to the API key. A self-host keeps the switch and the warning: whoever runs it carries the terms.

The apps say it where it matters. The plan's panel ends with who the agents answer ("On your plan, Ada only replies to you."). Where every agent with an AI answers only the person setting up, the setup's Team step says so before anyone is invited, since someone invited then has no agent to talk to. On the Cloud the agent's page shows "Only replies to you" as a fixed line, with no switch.

*Amended 2026-10-29:* every setup allows it, the Cloud included, and nothing asks to accept the terms. The switch is "Replies to everyone" ("Responde a todos"), off by default: an agent on its owner's plan replies only to them until they turn it on, then to everyone its own "who can talk" setting lets in. A switch onto a plan still starts owner-only, only the plan's owner turns it on, and admins only narrow. Under the switch a short line says the plan's terms are a gray area here ("A gray area in Claude's terms", ChatGPT's, or the plan's for a coding plan), and its ⓘ says what they say, for a plan or for a seat. Turning it on or off is audited as any change of who may talk to an agent (`agent.audience_changed`), and nothing records an acceptance. The 2026-10-27 rule for the Cloud is gone (`plan.personal`): the gate reads the stored audience everywhere. The API still takes `acceptPlanTerms`, which older phone apps send, and ignores it. The confirmation dialog, the panel's fixed note and the Cloud's fixed line give way to the same switch, line and ⓘ: in the plan's panel (the setup's AI step and Connect an AI, for one agent or for all of them) and on the agent's page, on the web and the phone. Someone who isn't the plan's owner sees whom the agent replies to and who decides. Before a sign-in the panel's switch waits, and the move onto the plan carries it.

*Amended 2026-10-30:* people read the switch and its ⓘ and still didn't know what it did: "Responde a todos" reads like email's reply-all, and the line under it spoke of a risk, not of the switch. Only the words and the line change; every rule above stands. The switch is "Answers other people" ("Atende outras pessoas"; for every agent of a plan's panel "Answer other people", "Atendem outras pessoas"). The line under it says what the switch does in its current state, with the agent's name and the plan: off, "Ada answers only you, on your Claude plan." ("A Ada só atende você, pelo seu plano do Claude."); on, "Ada answers anyone who can talk to her, on your Claude plan." ("A Ada atende quem pode falar com ela, pelo seu plano do Claude."); for every agent "They answer only you…" and "They answer anyone who can talk to them…". A seat says "your Claude seat" and a coding plan its own name ("your GLM Coding plan"). The terms move behind that line's ⓘ ("About the plan's terms"), in plain words: "Claude plans are for personal use. Letting other people use yours is a gray area in Claude's terms." ("Os planos do Claude são para uso pessoal. Deixar outras pessoas usarem o seu é uma zona cinzenta nos termos do Claude."), each seat being for one person, or a coding plan's maker's own words, in the same shape. Someone who isn't the plan's owner sees "Answers only João" ("Só atende João") or "Answers other people", with "Ada thinks with João's plan. Only João can let other people talk to her." ("A Ada pensa com o plano de João. Só João pode deixar outras pessoas falarem com ela."), which is also what "Who can talk" says when an admin tries to widen it. The toasts, their buttons, the refusal, the note before inviting and New agent's note on a plan use the same verb ("answers", "atende").

*Amended 2026-11-03:* an admin lets other people in too, not only narrows: "Atende outras pessoas" and "Quem pode falar" work for them as for the plan's owner, the same switch, line and ⓘ, the line naming whose plan it is ("A Ada só atende Walter, pelo plano do Claude de Walter."). The admins, who already choose who talks to every agent, carry the plan's gray area as its owner does; the change is audited as any (`agent.audience_changed`). The refusal `audience.plan_owner_only` and the read-only line for someone who isn't the plan's owner are gone.

*Amended 2026-11-03, later:* the plan's owner still decides by default: an agent that moves onto a plan answers only them, and a member who doesn't own it can't widen it. Someone who may change who talks to it (`manage_agents`, through any role that grants it, the owner role included) may still let more people in, but it spends someone else's plan, so it is asked and told. Before any save that widens its audience ("Quero falar com ele/ela", "Deixar Ana falar com ele/ela", "Quem pode falar" on the agent's page and in its profile card, "Atende outras pessoas" in Configuração avançada), the apps ask one question: "Usar o plano de João?", saying conversations with the agent will use João's Claude plan and its limits, and that João gets an email. When the save also takes a mailbox someone gave the agent, the mailbox's sentence follows in the same dialog (`widenQuestion`). The change is audited as any, with whose plan it is (`planOwner` in `agent.audience_changed`), and when it lets more people in and wasn't the plan's owner's own, the outbox job `agent.plan_opened` (queued in the same transaction, `audienceChanged`) sends the owner one email in their language through `email.send`: who changed it, the agent, who could talk to it before and now, and a button to its "Quem pode falar" to undo it. The subject is our words only ("More people can talk to your agent on your Claude plan"), as for every email: names people type stay in the body. Narrowing, and the owner's own changes, send nothing.

Moving an agent onto a plan counts as opening that plan to whoever it then answers: an admin who moves it with "Atende outras pessoas" on is asked the same question and the owner gets the same email, even when it answered the same people on the API (the email says only the owner could talk to it on the plan before). Only a plan of its owner's counts: the apps ask when its brain line names the sign-in it thinks with (`account`), and the job sends nothing unless its owner's plan thinks for it there and they are still in the workspace (`planIsOwners`), so OpenCode's free tier on a computer nobody connected (ADR 0132) asks nothing and emails nobody. The question names the plan as the email does: a coding plan's own name ("Z.ai"), else Claude's or ChatGPT's.

*Amended 2026-11-12:* a move onto a plan is from the API key, or onto a plan that changes hands. An agent already on one of its owner's plans that goes to another kind of plan of theirs (Claude to ChatGPT) keeps whoever its owner let in, as it does when only the account or the model changes: people picking another model that way found the agent answering only them again (`nextAudience` in `brain-settings.ts`). When that opens the other plan through someone else's change, its owner still gets the email (`agent.plan_opened`).

### 6. The sign-in code never passes through our servers in the clear

ADR 0041's path stays: the provider's own CLI signs in on the computer, the pasted code is sealed in the browser to a key made inside the runner (ADR 0027), and the server relays the ciphertext in memory, never storing or logging it. Claude's flow uses PKCE (S256), so a relayed code is useless without the verifier that never leaves the CLI. The paste is the only hard step: the sign-in opens in a popup, "Paste" sends by itself only when the text ends with this sign-in's state, and an optional "Which account?" email becomes the CLI's login hint (validated, never passed to a shell). Each sign-in runs the provider's CLI on a computer others may share, so a computer runs at most four at once and a person starts at most ten per computer every 15 minutes.

*Amended 2026-10-28:* the apps ask for no address: the account chosen on the provider's own page is the one connected. The API still takes the optional email (older phone apps send it), and signing in again to a signed-out account sends that account's own email as the login hint, unseen. A new sign-in that comes back as an account its person already has on that computer is refused as before, and the answer now carries that account, which they may think with instead for an agent while it is signed in and no agent thinks with it. Signing in again that comes back as another account (an email other than the account's own, or one its person already has there) is refused too: the account stays signed out with its agents, never removed, and the answer says which account came back (`signedInAs`). That login stays in the account's folder until it signs in again or is removed; nothing thinks with a signed-out account.

### 7. Usage limits, read without touching a token

Each account's usage comes from the CLIs themselves: the rate-limit events during turns and a usage request that makes no model call (Claude Code), the app-server's rate-limit calls (Codex), and the provider's usage endpoint for a coding-plan key, called from the computer. The server keeps percentages and reset times only. The meter shows each window, tightest first, warns at 80% and says until when an account is at its limit. Accounts never switch by themselves.

*Amended 2026-10-31:* the bars say it too. Each window's bar is ink below 80%, amber from 80% and red from 90% and at the limit (`planLevel` and `PLAN_TONE` in `packages/ui/src/plan-state.ts`, on the web and the phone), and the words above the bars take the plan's level: the tightest window's, or at the limit when the plan refused a request, so a refused plan reads red over bars that may still be ink. The percentage and the words stay beside the color, which is never the only signal, and only plan meters change: budgets and the other meters stay ink. The runner sends the usage at once when a window crosses 80, 90 or 100, and an OpenCode window whose status is `rate-limited` reads as full, whatever its percent says.

Usage and cost are recorded per agent as for every model call. *Amended 2026-10-27:* Gemini joins through its own adapter on Google's Interactions API (ADR 0018), with an API key only: Google's AI Pro and Ultra plans are served through Antigravity, whose terms forbid using the service in other products or through third-party tools.
- **Coding plans** (GLM Coding Plan, Kimi Code, MiniMax, OpenCode Go) run only on a computer, through Claude Code with a base URL, as a "key account". The plans' terms allow only coding tools, so our server never holds, routes or sees a plan key.

  *Amended 2026-11-06:* a plan with a public list of models (`modelsUrl`, OpenCode Go's today) follows it: each server reads it at boot and every hour and sends it to the apps with `/api/app/models`, so a model OpenCode adds shows up without a release. The computers never read the list: they map the aliases from their own table and take the id the server chose (`planForTurn`). - A key account's turn gets the key in the process environment only (redacted from everything the runner sends) and keeps Claude Code's model aliases, each mapped to the plan's own models; no CLI signs in or out there, and a key its endpoint refuses reads as signed out until a new one comes. A sign-in account's turn pins Anthropic's own endpoint the same way, and a turn on the computer's own sign-in pins the endpoint, cloud and proxies the runner itself runs with (unless the computer's owner chose to load their own Claude Code settings). *Amended 2026-10-30:* a plan offers every model of it that answers through Claude Code, not only the ones its aliases name: the plan list holds each one with a tag from its plan's or maker's own words (cheap, fast, flagship), the alias it runs for, if any, what the plan's account must allow before it answers (OpenCode's Global region, for DeepSeek's models) and, on a plan that sells several makers' models, its maker, by which the pickers group them, as each maker documents them (OpenCode Go: 24 models, Kimi Code: 6, GLM Coding: 2, MiniMax: 1; OpenCode Go's free models and the ones that train on what they are sent stay out).   *Amended 2026-11-06 (one OpenCode Go model):* on a plan whose models each have their own limit (`limitsPerModel`, OpenCode Go), every alias, Claude Code's small model and its subagents run the turn's model, so an agent on one model makes no call on another; a task carries the agent's model too. - Account folders are secret paths for agent file operations, and environment names reserved for providers and the runtime are refused as agent secrets.

## Risks we accept

- **Terms.** Anthropic says personal subscriptions are for personal use and that "developers may not collect, store, or intermediate Claude.ai credentials or session tokens". OpenAI's Sign in with ChatGPT terms say: "Another user's activity must not trigger requests to the authenticated user's account." Z.ai says "Account sharing or multi-user access is prohibited" and limits the GLM Coding Plan to "officially supported tools and products"; MiniMax describes its plan as individual, interactive developer use; OpenCode Go plans "are for single-member workspaces" (all read 2026-10-23). Our server never sees a sign-in code or a plan key in the clear, and a plan answers only its owner until the owner turns on "Answers other people", whose ⓘ calls the terms a gray area, in every setup (§5). That change is audited like any other of who may talk to an agent. An owner-only autonomous agent on a Z.ai or MiniMax plan is still a gray area.
- **Several seats.** One person running several seats as several agents sits close to the usage policies' "bypassing restrictions". Accounts never switch by themselves; moving an agent to another of the owner's accounts is always the owner's own choice.
- **Logos.** Anthropic's brand terms rule out its names and logos in "your own product, feature, or company name" and say any other use "requires our written permission"; MiniMax keeps all rights to its drawing. We show marks only to say which provider something is, never redrawn and never in our feature names, and one data file means removing or swapping a mark is a one-line change.
- **A token for all agents.** Where each agent is its own OS user, the runner keeps a person's `claude setup-token` token for their agents (§2, amended 2026-10-30), which Anthropic's sentence about storing credentials may be read to cover. `SHARED_SIGN_INS.claude_code` set to false goes back to one login per agent there.

## Consequences

- Positive: a team's seats become distinct, owned rows; any member can bring a plan to the Cloud or the server's computer; a plan never answers someone else by accident.
- Positive: four more API providers through one adapter, coding plans without our server ever holding a plan key, and logos from one source on every platform.
- Negative: more states to keep straight (a sign-in in progress, removing, signed out) and a new migration, runner protocol fields and screens.
- Negative: the providers' printed CLI output and usage endpoints can change; tests use fake CLIs, and a usage source that breaks only empties the meter, never a turn.

## Alternatives considered

- **A direct-to-computer endpoint for the code**, so it never crosses our server. Computers sit behind NAT, and on the Cloud we would issue the endpoint's TLS name ourselves, so it would be no more private than the sealed relay. Rejected.
- **Per-person routing to the workspace key**: the plan for its owner, the workspace's API key for everyone else. One agent would think with two brains and two costs depending on who is talking, and its sessions would split. The audience gate does the job. Rejected.
- **Switching accounts automatically at a limit.** Rotating subscriptions to get around limits can break the providers' terms (ADR 0041 §6). Rejected.
- **One sign-in folder for several agents' OS users** (a group, ACLs). Claude Code and Codex rewrite their credentials file readable only by the user who refreshed it, so every other agent loses it at the first refresh. Rejected. *Still rejected (2026-10-30):* nothing is shared as a folder across users; root keeps the sign-in and hands each turn a credential (§2).
- **Copying a login into each agent's folder.** The copies race on a rotating refresh token, and for Claude our code would handle a session token. Rejected. *Still rejected for copies that run at once (2026-10-30):* Claude needs no copy of a sign-in, since `claude setup-token` makes a token for headless use that is never refreshed; ChatGPT's `auth.json` is to go to one turn at a time and come back refreshed, as OpenAI documents for automation.
- **`claude setup-token` kept by the runner and given to each turn.** It holds across users (no refresh), but our code would store a Claude.ai credential, which Anthropic's terms forbid, and such a token can't read the plan's usage. Rejected. *Taken up 2026-10-30 (§2):* the token is the person's, made by the unmodified CLI through Anthropic's own flow, kept on their computer or their workspace's for their own agents, behind a switch; the plan's usage still comes from the turns' rate-limit events, only the usage request is lost.
- **Taking turns on one folder**, lent to whichever agent runs. Agents would queue behind each other's turns, which take minutes, and the router starts up to two at once. Rejected. *Still rejected for Claude (2026-10-30); the way for ChatGPT where each agent is its own OS user (§2):* the other choice there is one agent per ChatGPT account, and OpenAI documents serialized use.
- **One OS user for all of one person's agents.** It would give one sign-in to every agent of a person and drop the isolation between them (files, browser profiles, processes, ADR 0057). Not now.
- **Storing plan keys on the server**, encrypted like workspace keys. The coding plans' terms allow only their coding tools, and a server-held key could be routed anywhere. Rejected.
