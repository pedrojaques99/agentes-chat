# 0023. Wiki: pages with versions, `[[links]]` from anywhere, agents write only on request

- Status: Accepted
- Date: 2026-10-15

## Decision

**Model.**
- `wiki_pages`: org, `slug` (unique among live pages), `aliases` (earlier slugs), title, markdown body, folder path (`Processos/Vendas`), tags, `version`, `locked`, `source` ("Salvar na wiki"), who created and last updated it, and soft delete.
- `wiki_page_versions`: one row per save, with the full text, author, the person an agent wrote for (`requested_by_user_id`) and a note.
- `wiki_links`: `(from_type, from_id) → to_slug` with `to_page_id` (null while the target doesn't exist). Sources are pages, messages and issues, so backlinks and the graph come from one table.

**Slugs.** The slug is the leaf title, slugified, with no folder (`[[Processos/Guia de Deploy]]` → `guia-de-deploy`), the same rule as the web app. A rename moves the old slug to `aliases`, so old links (in messages, issues, bookmarks) keep resolving. Pages that link to the renamed page get their `[[…]]` rewritten, each as a new version. Messages are never rewritten.

**Links.** `[[Título]]`, `[[slug|texto]]` and `[[Página#seção]]` are parsed on save; code spans and blocks are skipped.
- Every message insert with `[[` records its links in the same transaction (`insertMessageWithRuns`), and so do issue descriptions.
- A new or restored page claims the links waiting for its slug. A deleted page releases them.
- Messages carry `meta.wikiLinks` (target, label, section, slug, title, exists), resolved when read and when published live, so a page created later shows as existing.
- `POST …/wiki/resolve` resolves links for issues and documents.

**Edits.** Saves are optimistic: `baseVersion` must equal the current version, else 409 `version_conflict`. A name already in use is 409 `slug_taken`. `ConflictError` now carries an API code.

**Access.** Every member reads; members create and edit; admins lock a page (then only admins edit it, and never agents). Every write is audited (`wiki.page_*`) and announced as `wiki.page.updated` (org broadcast, with `action`).

**Search.** Pages are indexed in the hybrid search as kind `wiki`, with no channels (the whole org reads them), and they are part of reindexing.

**Agents.**
- `wiki:read` (on by default, backfilled): `search_wiki` and `read_wiki_page`.
  - Each run gets the relevant pages in its prompt: the ones the message links, then search hits, within a budget.
  - They come under "Wiki da organização (fonte confiável)", ranked above memory.
- `wiki:write` (on by default, backfilled): `create_wiki_page`, `update_wiki_page` (append, replace a section, or replace with `base_version`) and `link_to_wiki`.
  - The prompt says to write only when a person asks in the current message.
  - The tools enforce it: the trigger must be a person's message. Agents' own messages and reminders are refused.
  - Every agent version records the agent and the person who asked ("por Theo, a pedido de Walter").

**"Salvar na wiki".** A message (that the person can read) either becomes a new page (`POST …/wiki/save`) or is appended to one (`POST …/wiki/pages/{slug}/append`). It is saved with a line saying where it came from, and new pages keep `source`.

## Consequences

- Links are stored per source, not per occurrence: two links to the same page from one message are one backlink.
- Rewriting links on rename is a loop over the linking pages inside one transaction. That is fine for hundreds of pages; a huge wiki would need a job.
- The trigger-based write check is coarse on purpose. A person's message that does not ask for the wiki still passes the code check, and there the prompt rule is what holds.

## Addendum (2026-11-01): pages limited to an audience

Some pages hold context the agents need but not every member should read (margins, salaries, a client's terms). A page can now be limited to an audience, with the workspace's roles (ADR 0085) instead of a permission system of its own.

- **Who sees it.** `wiki_pages.restricted` with `audience_role_ids` and `audience_user_ids` (migration `0149_wiki_visibility`). A restricted page is seen by owners, the people holding one of its roles and the people named in it. "Only admins" is the "Admin" role; both lists empty is owners only (agents follow their own list, below). A deleted role matches no one.
- **Who sets it.** People who hold both `edit_wiki` and `manage_roles` (`PUT …/wiki/pages/{slug}/audience`, `null` opens it again), on a page they see and may edit (a locked page still needs `configure`). The audience must include whoever sets it (`wiki.audience_excludes_you`), so nobody hides a page from themselves; owners always see it. Audited as `wiki.page_restricted` / `wiki.page_opened`.
- **Everywhere a person reaches pages.** One SQL condition (`wikiPageVisibleSql` in `wiki-links.ts`) keeps people outside the audience from the list, the tree, `[[` suggestions, the graph (no edge and no "unresolved" slug to it), wiki search, the workspace search (`searchForUser` drops its hits: the index stays org-wide so agents find it), backlinks from it, the page's own links to it (shown as not written) and "what the agents read most". Opening it, its history, a version or any write is a plain 403 `wiki.no_access`, and the apps show "Você não tem acesso a esta página".
- **Links written in messages.** `meta.wikiLinks` is resolved once for every reader of a channel, so a link to a restricted page carries `restricted: true` and no title: the text shows what the author wrote, and opening it follows the rule above. The web and phone resolve links against the reader's own page list, so there it reads as a page not written yet. A new page named like a hidden one takes the next free slug instead of a `slug_taken` that would name it.
- **Agents.** Agents read a limited page only within what the people around them see: see "Addendum: a run reads for its readers" below, which replaces the rule this addendum first had.
- **Titles never leak through conflicts or renames.** Creating or renaming onto the address of a page the writer (or the person an agent writes for) doesn't see takes the next free address instead of `slug_taken`. A restore blocked by a page at its address says so without that page's title. Renaming a restricted page doesn't rewrite `[[…]]` in the pages that link to it: the old slug stays as an alias, so those links still resolve, and the new title stays out of pages its audience doesn't cover.
- **People leaving.** Removing a member also removes them from every page's `audience_user_ids`, so rejoining later doesn't give a restricted page back.
- **Broadcasts.** `wiki.page.updated` goes to every member, so for a restricted page it carries only `{ id, restricted: true }`.
- **Agents are chosen too** (see "Addendum: agents and folders" below, which replaces "every agent of the workspace" here).

## Addendum (2026-11-01): agents and folders

A page's audience stopped short of what a team with private pages needs: every agent still read every restricted page, and thirty pages of a folder had to be closed one by one, with a new page born open. Agents hold no roles (ADR 0085), so they are a list of their own, and folders copy their audience onto pages, so one condition over `wiki_pages` keeps deciding who sees what.

- **Agents.** `wiki_pages.agents_limited` with `audience_agent_ids` (migration `0168_wiki_agents_and_folders`), independent of `restricted`: a page can be open to every member and read by two agents. The default is every agent, so pages already limited keep working as they did. An agent outside the list gets nothing: not in its run's context, `search_wiki`, `read_wiki_page`, `search_context` or a mission's `get_context`, and it can't write the page; to it the page doesn't exist (`wiki.page_not_found`). This is enforced in the queries (`wikiPageAgentVisibleSql`).
- **Search that spans everything.** `search_context` and `get_context` handed agents wiki snippets with no check. Both now go through `wikiHitsForAgent`.
- **Folders.** `wiki_folder_audiences` holds a folder's audience (`PUT …/wiki/folder-audience`, both `null` opens it; same permission as a page). Saving copies it onto the pages in the folder and its subfolders, deleted ones included, and `wiki_pages.audience_folder` records the folder a page follows. A page created, imported or moved in takes it. Each change takes a per-workspace advisory lock.
- **A page or subfolder can only be narrower** than the closest limited folder (`wiki.audience_wider_than_folder`), so nothing inside a closed folder opens by mistake; to open a page, change the folder. A list next to a folder's list keeps what they share (`clampTo`): a person stays if the folder names them or they hold one of its roles. So when a folder narrows, a page with its own audience may end up with nobody but owners, which fails closed.
- **Moving.** A page moved out of a limited folder keeps its audience, as its own. A limited page moved into another limited folder is cut to fit it rather than taking it, because moving needs only `edit_wiki` and must not widen anything. A move or a create that would leave the writer, the person asking or the agent outside the page is refused (`wiki.no_access`), which tells someone guessing a limited folder's exact name that it exists; that beats a page vanishing from its author.
- **Opening a folder** opens only the pages that followed it. Pages with their own audience stay limited.
- **What a list can't undo.** Taking an agent off a list stops what it reads from then on. Notes it already saved stay, and so does what a live computer session already read. Someone inside an audience can still copy text elsewhere.
- **Folders aren't things.** A folder is text on its pages, so a rule stays on its path when the last page leaves, and the next page there takes it.

## Addendum (2026-11-01): who edits

Seeing a page and editing it were one thing: whoever saw it and held `edit_wiki` could change it, and a lock was all or nothing, for admins only. A team needs "Finance edits, Sales reads" on the same page.

- **A level for everyone and one per row.** Reading "Quem vê" as three levels (no access, view, edit) on "everyone" and on each role, person and agent: one list in the apps, for people and agents apart. It saves as `editors_limited`, `editor_role_ids`, `editor_user_ids`, `agent_editors_limited` and `agent_editor_ids` on `wiki_pages` and `wiki_folder_audiences` (migration `0169_wiki_editors`). The mapping lives in the client (`wikiAccessDraft`, `wikiAccessOf`), so the web and the phone can't disagree.
- **Editing narrows seeing, and never grants.** To edit you must see the page, hold `edit_wiki` (an agent: `wiki:write`) and be on the list when there is one. Owners always edit. A lock still applies on top. The list doesn't lift a missing `edit_wiki`: a page can't give what a role takes away, and the apps say so.
- **Every write is covered.** The check is in `requireWriter`, so saves, renames, moves, deletes and restores all follow, as `wiki.edit_limited`. An agent needs its own place on the list and, when acting for a person, theirs too, so nobody edits through an agent what they can't. `read_wiki_page` tells the agent a page is read-only for it.
- **Folders.** Editors follow the same rules as the audience: copied onto pages, taken by pages that land in the folder, and a page or subfolder can only narrow them. So a folder can be read-only for most people: creating or moving a page into it needs being on its editors.
- **Nobody locks themselves out.** Whoever sets an editors' list stays on it (`wiki.editors_exclude_you`); owners are exempt.
- **Pinning stays apart.** "Fixar" arranges the wiki for everyone and doesn't change the page, so it isn't subject to the page's editors.

## Addendum (2026-11-01): a run reads for its readers

The first version let any agent read a restricted page and told it, in the prompt, not to repeat it to someone outside. That holds only as well as a model follows it, and a page of salaries can't rest on that: a member could ask an agent for what they can't open, and a persistent enough question, or a decision that gives the answer away, gets it out. An agent's output reaches people, so what it may read has to be decided by who those people are, before the text reaches it.

- **The rule.** A run reads a limited page only when the agent, the person behind the run and everyone who reads its conversation all see it (`wikiPageRunVisibleSql`, one condition in every read). Otherwise the page isn't there: not in the run's context, `search_wiki`, `read_wiki_page`, `search_context` or `get_context`, and the agent can't tell it exists. `RESTRICTED_WIKI_RULE` is gone: no agent holds text it was told to keep from someone.
- **The person behind the run** is the one gate of ADR 0053 (`authority.ts`), which follows a chain of agents back to the person at its root. So asking an agent to ask another doesn't launder access: the second run still reads for the person who started it.
- **Who reads a conversation.** Its members, people and agents; for a public channel, the whole workspace, members of it or not. So a person in the audience asking in a channel with someone outside gets no page there, and a DM or a private channel of the audience does.
- **The answer goes to their DM.** When only the conversation keeps a page from a run (the agent and the person who asked may read it, and the message names it, it is the best match, or the agent asks for it), the server sends their question to the agent's DM with them and that run answers there (`sendHeldToDm`). It is the server's decision, once per run, and only for a person's own message. The run in the channel gets a line saying the content is restricted and goes by DM, with no title and no text, and says so: saying that something restricted exists is accepted, its title and text never leave. The note in the DM is an `agent_note`, a kind every app already keeps out of the conversation, so this needs no new app.
- **Nobody behind it.** A routine reads with its creator's access, the reach it already has (ADR 0053 §2). Any other run with nobody at its root (an agent's own work) reads no page limited to people. It fails closed.
- **What this gives up.** "Agents use it to decide without showing it" is gone on purpose: a page only agents and owners see can't feed an answer to a member, because that answer would carry it. Someone reading the channel can tell that something restricted exists on what was asked.
- **What it doesn't cover.** It decides what a run may read, not what happens after. Someone in the audience can still ask an agent, in a private place, to post a page elsewhere, as they could copy it themselves. A routine's report can reach further than its creator's page does if its instructions send it there. Memory an agent already kept stays where it was kept.
- **One access list, for here and later.** The apps ask this as one list, the way people share a document: "everyone", "all agents" and then whoever is added, each with a level. The web's is `AccessDialog` (`packages/ui`) and the phone's `AccessList` (`apps/mobile/src/features/shared`); neither knows what it guards, so a channel, a Drive file or an agent can use them by giving the people and the levels. Only `WikiAudience.tsx` on each side knows the wiki's rules. In the apps it is now called "Acesso", since it says who edits too.


## Addendum (2026-11-02): editing the page as it reads

Editing was a Markdown text box in a code font, in a fixed-height pane: tables became pipes and dashes, links brackets, and people who don't write Markdown couldn't change a page. The page also read in a narrow column between the tree and a side column, so tables were cut.

- **The page edits as it reads.** The editor (`WikiRichEditor`, `apps/web`) is the page's own `.md` elements made editable, with a toolbar that stays on top (the block the caret is in, marks, lists, tasks, a page link, a table, a callout, code), `[[` to link a page and `/` for the blocks. It is ours, on the browser's editable text, with no editor library: the page keeps one renderer and the design system its own controls.
- **Markdown stays the format.** Agents, search and Obsidian read Markdown, so the editor saves Markdown (`@/lib/wiki-rich`), reading back only what the reader draws. The parser can return each block's source lines (`parseMarkdown(…, { ranges: true })`), and the editor keeps them: a block nobody touched saves exactly as it was written, and a page opened and saved without a change saves the same text. So syntax the reader doesn't draw (wrapped lines, nested lists, an import's quirks) survives an edit elsewhere in the page. Pastes go through the same path, so only what the page draws comes in. "Markdown" switches to the text itself for whoever prefers it.
- **What isn't saved stays.** The draft (title, folder, tags, text and the version it started from) is kept in the browser's book of unsent texts, so leaving a page and coming back picks it up; saving or "Cancelar" clears it. A save from an old draft still meets the version check.
- **Asking an agent.** Selected words (or the whole page) can go to an agent: the person's message, with the words quoted and a link to the page, goes to their DM with it. The agent edits with its wiki tools, so the version reads "a pedido de", and nothing new on the server was needed.
- **One column.** The outline moved into the tree, under the open page; who sees the page and the agents that use it moved to the line under the title; mentions, the agents' reads and the history to the end of the page. The trail and the page's actions sit on a bar that stays on top, so a long title never shares its line with buttons.
- **Two fixes.** A title with "/" given with its folder apart (as an agent does) kept only its last part; now the title stays whole, its slashes as division slashes (∕), since a "/" in a title names a folder in links and paths. Renaming never moves, so it keeps slashes the same way. A mention in a DM showed the DM's internal name; backlinks now say who the conversation is with (`dm`).

## Addendum (2026-11-06): the same control as a task, and administrators

ADR 0151: who sees a page is the same three options as a task, on a new page and on the page, for anyone who edits it. Agents and editors still take `manage_roles`. Administrators, not only owners, always see and edit. An agent's page takes the people of its conversation from a DM or a private channel, and a run's rule for reading stays as above.

## Addendum (2026-11-06): big imports, cleaning up, and what goes into a run

A vault of 347 notes came in as 200 with no word about the rest: the app sent batches of 200, a failed second batch ended the import, and one note past a field limit failed its whole batch. Deleting the 200 meant one page at a time, the trash had no screen, and every run got up to five pages because any common word matched.

- **Imports end honestly.** The server checks each note and puts the ones it can't take in `failed` (a body over 200,000 characters, no usable title); tags, aliases and attachment names past their limits are cut. The app checks the same before sending, sends batches by count and size, tries a failed batch again, and ends with what came in, what didn't and why, and "Tentar de novo" for the batches that failed. Every batch carries the import's id (`source.importId`): a note that import already brought (same folder and title, same person) comes back as in instead of being made again, so a batch whose answer was lost, sent again by the app or by "Tentar de novo", never doubles.
- **Deleting many.** A selection, a folder with its subfolders, or everything from one import (by its id, or by the vault's name for imports made before ids) goes to the trash at once (`deleteWikiPages`). Pages the person can't delete stay and are counted.
- **The trash.** Deleted pages stay 30 days, as the Drive's files do (ADR 0111), then the `wikiPurge` worker removes them with their history. The wiki's "Lixeira" restores one or many and deletes for good, one or all.
- **The root has an audience.** The root ("") takes a folder's audience, which reaches every page and folder below it. For the pages at the root alone, the agents' access can be set for a selection.
- **What goes into a run.** The search drops Portuguese and English stopwords and ranks by how dense the matches are (`ts_rank_cd` normalization 2|32), doubled when the title has one of the words. The title only multiplies: a common word in many titles doesn't lift a long page that barely mentions it. A run takes a page only when its density reaches `WIKI_MIN_RANK` and it matches two of the message's words or one in its title; vector hits only reorder those, and without the index a run gets none. On a 200-page vault (`packages/engine/test/wiki-corpus.ts`) each of 14 questions gets its page first and 10 messages about something else get nothing. `[[named]]` pages still go in, ahead of the pages always in context.
- **Always in context.** "Sempre no contexto dos agentes" puts a page in every run of an agent that reads it, as if the message named it, at most three per workspace so the budget holds. "Fixar" stays for people. To keep a page from agents, its agents' list does that.
- **What the agents read most** counts pages an agent opened with `read_wiki_page`; a page that only went into a run's context doesn't count there (`wiki_page_reads.kind`). The page's own "agents that use it" counts both.

## Addendum (2026-11-12): one import, from several places

- **"Importar" asks where from.** The wiki's import is one dialog with the source as tabs (Obsidian, GitHub, Files), and its entry points carry no app's mark. Whatever the source, the app ends with the same files in the browser, so the review, the batches, "Tentar de novo" and deleting an import as one are unchanged. A page keeps where it came from (`source.type`: `obsidian`, `github` or `files`); files dropped on the page are a vault when they carry Obsidian's own folder, else `files`.
- **A GitHub link** (a repository, a folder or one Markdown file) is read on the server: `GET …/wiki/import/github?url=` answers a zip of the Markdown notes at or below the link and the files beside them a note may embed (while they fit in 100 MB, 50 MB a file, 5000 notes), paths relative to the link; hidden files and folders and `node_modules` are never read, and nothing is saved. A private repository is read through the workspace's GitHub as a skill's link is (ADR 0156), for who edits any agent; when none reaches it the dialog offers "Conectar o GitHub" and reads the link again (`packages/engine/src/wiki-github.ts`).
- **Plain Markdown embeds.** `![alt](images/chart.png)` with a relative path becomes `![[images/chart.png]]` on import, so a repository's images go to the Drive and show on the page as a vault's do; links to the web and code blocks stay as written.
