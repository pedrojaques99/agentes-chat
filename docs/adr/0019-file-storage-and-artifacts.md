# 0019. File storage per organization, and artifacts

- Status: Accepted. Amended 2026-10-30 by ADR 0088 (deleted workspaces go at the end of their 7 days; a deleted account's photos). Amended 2026-11-01 (a page has no network)
- Date: 2026-10-14

## Decision

**Blob stores.** Files go through a `BlobStore` (put, get, delete, list, signed GET URL). Implementations: S3-compatible buckets (a small SigV4 client over `fetch`, no SDK, so tests swap the transport for an in-process fake server), Postgres (fallback when the deployment has no bucket; can't sign, so downloads are streamed), and memory (tests). Platform storage is our bucket from `S3_*` (Cloudflare R2), one key prefix per org (`orgs/{orgId}/`); without `S3_*` it is Postgres. Objects are private.

**Deleted workspaces.** A workspace deleted with its last member's account leaves platform storage through the job `org.files.purge`, enqueued with the deletion and without `org_id` (the row would go with the workspace): its keys under `orgs/{orgId}/` and its logo under `org-logos/{orgId}/`. On disk (`FILES_DIR`) each folder goes at once with the folders inside it (`deletePrefix`). Elsewhere a run deletes 1,000 keys of each, and the job runs again while a page comes back full. It keeps trying through a storage outage for about 30 days (240 attempts). A second pass a day after the deletion takes files that work under way stored after the first. It never touches a workspace that still exists. A bucket the workspace brought stays its own.

*Amended 2026-10-30 (ADR 0088):* every workspace is deleted at the end of its 7 days by the `org.delete` job, whoever asked (an owner, or the account of its only member), and that job queues `org.files.purge` and its second pass in the transaction that deletes the row. A deleted account's photos (`avatars/{userId}/`) leave platform storage through `user.files.purge`, queued in the account's deletion with no `org_id`: one page of 1,000 keys holds them all, since a new photo replaces the last, it keeps trying as long as `org.files.purge` (240 attempts), and it never touches an account that still exists. The route also deletes them at once, best effort.

**Per-org storage.** An org may bring its own S3-compatible bucket (R2, AWS S3, MinIO, Wasabi…): `storage_configs` keeps endpoint, region, bucket, prefix, path-style, the access key id, and the secret envelope-encrypted like provider keys (bound to org and row); only hints come back. Rows are immutable after the probe: new settings are a new row. Every blob read and write goes through `BlobStoreResolver.forOrg(orgId)` (where new objects go) and `forConfig(orgId, configId)` (where an existing object was written). Each artifact version records `storage_config_id` and its key, so switching storage never breaks old files; an admin-started job (`storage.migrate`) copies existing objects to the current storage and repoints them, saving progress after each object and resuming after a failure. Google Drive and OneDrive as storage are not planned: those services connect through Conectores (ADR 0107), and `storage_kind` keeps their values unused.

**Verify before activating.** `POST …/storage/test` writes, reads, lists and deletes a probe object and reports each step with a clear reason (key refused, bucket missing, wrong region, no permission, unreachable). `PUT …/storage` switches on only settings whose fingerprint (settings + keys) passed a test in the last 30 minutes. Only admins (`configure`) manage storage; tests, switches and migrations are written to `audit_log`.

**SSRF.** An endpoint typed by a person must be https, without credentials, not a `localhost`/`.local`/`.internal` name, and neither the host nor any address it resolves to may be private, loopback, link-local (cloud metadata), CGNAT, multicast or reserved. The same guard (`assertPublicHttpsUrl`) is for custom MCP URLs. DNS can change between the check and the request (rebinding); the guard still stops typed-in internal targets, and the S3 client never follows redirects.

**Artifacts.** `artifacts` (kind, title, channel and thread of origin, current version, creator and last editor, `untrusted`) and `artifact_versions` (storage, key, size, SHA-256, note, author, run). Kinds: `document` (Markdown), `table` (columns + rows, CSV export), `diff` (files with unified patches, `.patch` export), `html` (a self-contained page), `diagram` (Mermaid). Sizes and shapes are validated. Visibility comes from the channel: org-wide when there is none; people see channels they belong to and public ones; agents see their run's channel, public channels they are in, and org-wide files. A file you can't see is "not found". People create in the Drive or in their channels and save new versions of documents and tables (a stale `baseVersion` is 409); the creator or an admin deletes. Agents use `create_artifact`, `update_artifact` (`drive:write`), `read_artifact`, `list_artifacts` (`drive:read`) through the Tool Gateway; the reply carries `meta.artifacts`, and the channel gets `artifact.created` / `artifact.updated`. Artifacts are indexed for search (kind `file`) through the outbox with the channel's visibility. Downloads are short-lived signed URLs (5 minutes) after the visibility check, or our streaming endpoint, always as attachments.

**HTML is untrusted.** A page an agent (or a person) writes can contain anything. It is stored as is and flagged `untrusted`. The app renders it only in a sandboxed iframe served from a separate origin, never inline on the app's origin; our own endpoint serves it as an attachment with `Content-Security-Policy: sandbox` and `nosniff`. Agents reading it get it labeled as data, never instructions.

*Amended 2026-11-01:* "Separate origin" means the opaque origin of a sandboxed blob frame. The sandbox alone left a page free to send what it held to any address, and the card on a message runs it as soon as it shows, with no click and no approval: an agent led astray by something it read had a way out. So a page now starts with a fixed prefix holding its policy (`isolatedPage`, `packages/client/src/lib/isolated-page.ts`): no network, no outside script, image or font. It is a fixed prefix because inserting after the first `<head>` lands inside `<!-- <head> -->`. The app's own pages carry `frame-src` so a frame can't navigate itself away, which no policy inside it can stop. The sandbox gains `allow-forms`: a browser fires no `submit` without it, and `form-action 'none'` still keeps a form from leaving.

*Amended 2026-11-03 (which files keep versions):* Versions are for what is worked on over time: documents, tables, diffs, pages, diagrams, and uploaded files such as a PDF, a spreadsheet, a zip or code. A picture, a clip or a recording (`image/*`, `video/*`, `audio/*`) is a snapshot: an agent's screenshot of a page, a photo someone posted. A new one is a new file, never a version of the old, so the viewer shows neither the history nor "Enviar nova versão" for it, and `addFileVersion` refuses it (`artifact.not_versioned`) for people and agents alike: `upload_file` with `artifact_id` answers the agent before any bytes move, so it shares the picture again as a new file. The rule is by type, not by where the file was posted, because a PDF dropped in a chat is as much a living document as one uploaded in the Drive. A snapshot that already has versions from before keeps them and their history. The server says it once (`keepsVersions` in `packages/engine/src/artifacts.ts`, `versioned` on the artifact's detail) and the apps follow it.

## Consequences

- One code path for every store; the org's bucket is just another config row.
- Old files keep working after a switch without a migration; the migration is optional and safe to re-run.
- The Postgres fallback keeps development free of external services, but is meant for small files only.
- Self-host can also keep files on local disk (`FILES_DIR`).

## Addendum (2026-11-11): the address is checked again as every request connects

The check when an address is saved doesn't hold for later requests: a name can answer with another address afterwards, and a workspace's own bucket with virtual-hosted addressing is reached at `bucket.endpoint`, a name the saved check never saw. So every request to an address a workspace's people, agents or connected servers named goes through one fetch, `outboundFetch` (`net-guard.ts`), which is `publicHttpsFetch` (ADR 0146): the host is resolved and checked at that request, the socket goes to the checked address, and a redirect isn't followed. It covers the workspace's own bucket, a custom MCP server's sessions (a 307 or 308 that stays on the same origin is followed, each hop checked again), MCP OAuth's discovery, registration, token exchange and refresh, the icon a server lists, and `web_fetch` (its own redirects, each hop checked). The saved check stays, for its plain errors.

Addresses the operator sets by env (the platform bucket, a search or speech server) are trusted and never checked. Where the operator lets workspaces reach the server's network (`allowsPrivateEndpoints`, ADR 0146: self-hosted and closed to sign-up, or `MODEL_ENDPOINTS_PRIVATE`), `outboundFetch` is the plain `fetch`, as before, so a proxy set for the server keeps working (`allowPrivateOutbound` at boot).
