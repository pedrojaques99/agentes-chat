- Status: Accepted (built; computer brains are chosen per agent; missions run only on the engine, no flag). Superseded in part by ADR 0059 (§5: the plan warning shows when a plan would answer other people, not when it is chosen). Superseded in part by ADR 0077 (2026-10-28): §2's git on cloud computers (connected computers use the git proxy through the runner). Addendum 2026-11-10: on the web, "Quem pensa" is the dialog Connect uses from a conversation (ADR 0160, addendum), one change per screen. Amended 2026-11-12: Codex runs on Windows (runner protocol 60), a `plan` or `work` turn only inside MXC (see "Codex").

## Context

Agents think through the Model Gateway with an API key. People who pay for Claude Code or Codex want their agents to think with that instead, on their own computer, and missions already drive Claude Code and Codex through the runner (ADR 0029).

Today the pieces don't share a spine:

- `executor.ts` does everything for a model run: builds the context, owns the run states, calls the model, executes tools through the Tool Gateway, keeps the transcript, streams deltas, pauses on approvals and records usage.
- Missions have their own path: runner tasks, an `agentes` MCP server with mission-only tools, resumes by session id, an inbox, their own approval and decision plumbing.

Adding "an agent whose brain is Claude Code" as a third path would copy the run lifecycle, the tool layer and the approval flow again. Every rule (a new tool, a scope, an audit entry, a budget check, a streaming tweak) would have to land in three places, and they would drift.

## Decision

**One engine runs every agent turn. What changes is only the brain that thinks. Everything else — context, run states, tools, approvals, transcript, streaming, usage, events — lives in the engine and is the same for every brain. Missions run on the same engine.**

### 1. The brain interface

A brain receives a turn and returns a stream of neutral events; it never touches the database, tools or approvals directly.

```ts
interface Brain {
  kind: "model" | "claude_code" | "codex";
  /** One turn: context in, events out. Resumable from a transcript or a session. */
  run(turn: BrainTurn, io: BrainIO): AsyncIterable<BrainEvent>;
}
type BrainEvent =
  | { type: "text_delta"; text: string }
  | { type: "tool_call"; id: string; name: string; input: unknown }   // engine executes it
  | { type: "usage"; input: number; output: number; source: "api" | "plan" }
  | { type: "limit"; resetsAt?: string }                              // plan limit hit
  | { type: "done"; text: string }
  | { type: "error"; code: string; message: string };
```

- **Model brain**: today's gateway loop, unchanged in behaviour (budget check before the call, usage with cost).
- **Claude Code / Codex brains**: a session on the agent's computer through the runner (`--resume <session>`), stream-json parsed into `BrainEvent`s; usage recorded with source `plan` and cost zero.

### 2. Tools exist in one place

The Tool Gateway is the only source of tools, scopes, levels (consult / alter / approval / off, ADR 0016 addendum), approvals and audit.

- Model brain: the engine passes the gateway's tool list to the model and executes calls directly, as today.
- Computer brains: the runner's `agentes` MCP server becomes a **bridge** with no tools of its own. `tools/list` asks the engine for the tools this run may use; `tools/call` is executed by the engine through the same Tool Gateway with the run's identity. The mission tools (`update_plan`, `ask_decision`, `request_review`, `complete_mission`…) become ordinary gateway tools available when the run is in a mission thread.
- Connectors (GitHub, Linear, Sentry, Drive, org MCPs) are reached the same way: the executor never receives a connector token (ADR 0007). Plain `git` on a connected computer uses the runner's credential helper with a short-lived, branch-scoped token (ADR 0030); on cloud computers, the git proxy (ADR 0024).
- Claude Code's permission prompts (`--permission-prompt-tool`) and command policy (deny list, low-risk auto-approval, mission rules) are engine features shared by every computer brain, not mission-only code.

### 3. Approvals and pauses work the same

A gated tool call pauses the run (`waiting_approval` / `waiting_input`), whatever the brain. On the decision the engine resumes:

- model brain: calls the model again with the transcript (today);
- computer brains: resumes the session with the tool result ("approved: …" / "refused: …").

Blocking decisions and reviews in missions use the same pause/resume.

*Amended 2026-10-30:* the run goes on with the result in hand, whenever the decision comes.

- A computer brain's gated call is marked `inTurn` on its pending call while the turn that made it still runs. A decision's job that finds such a call while that turn's job still holds the run (an `agent_run.execute` job claimed, its lease live) leaves the run alone; the turn's end (`suspendedByBridge`) clears the mark and, when everything it waited on is already decided, queues the resume itself. The session never takes two turns at once. Any job that finds its run `running` under another live job returns too (two resumes of one pause, two decisions at once).
- On the resume the run keeps what was decided and what came back (`transcript.decided`). When the next final answer has no word from the agent (no text, no narration since its last message) and isn't a reaction or a mission report, the run gets one more turn that says to finish the task with what the call returned, then what was decided and what came back (`decisionNudge`, once per run, `nudged: "decision"` step). Each result is cut in its middle, so one inside an outside envelope (`<external_data>`) stays closed and nothing the run is told reads as outside data. Background runs keep speaking only through `hand_off`.

### 4. Context is built once

`context.ts` builds the run context for every brain. The model brain receives it as system/messages; computer brains receive it at session start (`--append-system-prompt` / first message) and fetch the rest through the same retrieval tools the gateway already exposes (search context, summaries, wiki, memory). The mission brief (ADR 0029) is part of this builder.

### 5. Choosing the brain

- Per agent: **Modelo (API)** (default), **Claude Code no <computador>**, **Codex no <computador>**, each with a model (`--model opus|sonnet|…`, `-m <model>`; `--fallback-model` for Claude Code). Only what the computer has is offered (runner detection, protocol 7). A mission can override the agent's brain and model.
- The agent keeps its audience. Choosing a plan brain shows a clear warning that the subscription is personal and that answering other people with it may go against the provider's terms; the person confirms and owns the risk. We don't block it.
- **Fallback, by what exists**: when the computer is offline, the executor isn't logged in, or the plan limit is hit:
  - if a model credential exists (the platform key on the Cloud, or an org/default key), the turn runs on the model brain and the reply carries a quiet note ("respondi pela API: o Claude Code no mac está offline"); that turn counts against the agent's budget;
  - if no model credential exists (a self-hosted install running only on plans), the agent says it is unavailable ("o Claude Code no mac está offline; respondo quando ele voltar") and the message waits in the run queue until the computer is back.
- **Speed**: computer brains keep one process per active thread (`--input-format stream-json`), closed after ~10 idle minutes and resumed with `--resume`.

*Amended 2026-10-31:* people pick what they pay for, not the program that runs it. A card read "Claude Code" with "DeepSeek V4.1 Flash" chosen under it, which made no sense to someone paying for OpenCode Go. "Quem pensa" now lists "Chave de API" (paid per use, on the agent's budget), "Claude" and "ChatGPT" (their sign-in opens in the card when nothing of theirs is there), then each coding plan with an account there that is the viewer's or that the agent thinks with ("OpenCode Go"). The chosen card opens into labeled fields: **Modelo**, only that plan's models (another card starts on its plan's default, Automático stays Automático, and coming back restores what was saved), with a note on how to give what a chosen model needs from its plan's account (OpenCode's Global region) and a link to the plan's site; then **Conta**, only that plan's accounts (the computer's own sign-in only on Claude and ChatGPT), where a refused key asks for a new one. Another plan on the same program is another account, which only the agent's owner picks (ADR 0059 §1–3): to anyone else that card is locked ("Só João troca"), while another program and the API key stay open to them. Claude Code and Codex are named only where the program is what is missing ("O Codex não está instalado no MacBook."), and the computer only where it changes something: a move, offline, or no computer having it. Every surface says what thinks in one sentence, the model by the plan that pays ("DeepSeek V4.1 Flash pelo OpenCode Go", `thinksWith` in `packages/client/src/lib/brain.ts`): the toasts, the agent's "Pensa com" cell (the model and its effort over the plan, or its account among two of that plan), the DM header, the profile card, "Usar em outros agentes" and the phone's "Pensa com", whose account list is the plan choice. Moving from the API onto a plan says that the agent now answers only its owner (ADR 0059 §5), in the same sentence as a move to another computer, and to anyone but that owner names them ("…e só atende João"), as the plan cards say whose plan it is ("Usa o plano do Claude de João"). On the phone an account of another plan says what thinks now, since the model changes with it. "Conectar outro plano" opens Connect an AI for the agent.

### 5a. The rest of the system also needs a model

Besides an agent's turn, several parts call a model in the background: the router (who answers), thread summaries, reflection and memory consolidation, the judge (low-risk command approval, connector tool classification, mention checks), thread titles, date parsing. On the Cloud they run on our key (and the fast judge) and are invisible.

For installs where only plans exist:

- **Default: a small model key for system tasks.** The self-hosted setup asks for one cheap model credential used only by these tasks (cents a month); plans do the agents' heavy work.
- **Graceful degradation when there is no key at all.** An explicit @mention always answers (no router); without summaries the context uses recent messages only; without the judge, "Só o que é arriscado" behaves as "Pergunta sempre" and connector tools default to "Pede aprovação"; titles fall back to the first message. Everything works, with less automation, and the UI says which automatic features are off.
- **Optional, later: system tasks on the executor** (short runs on Claude Code/Codex). No key needed, but slow and it spends plan limits, so it is opt-in.

### Editions

The engine is the same in both editions; only defaults differ: the Cloud encourages the model brain (usage through our gateway, budgets, no dependency on a person's computer, no plan-sharing risk) and offers computer brains as an advanced option with the warning; a self-hosted install with Claude Code or Codex on its computers can suggest them first. This is an edition default (ADR 0002 modules), not separate code.

### 6. Missions run on the engine

A mission's main session is simply the agent's run in the mission thread with the mission's brain; item work is runs/tasks of the same engine in their own branches or subfolders. The mission-specific runner path (its own MCP tool set, resume plumbing, inbox delivery as a special case) is replaced by engine features. Missions keep their data and UI (plan, decisions, reviews, deliveries, `.agentes/`); only the execution spine is shared.

## Order

1. Extract the engine and the `Brain` interface from `executor.ts`; the model brain is today's behaviour (existing tests guard it).
2. Runner MCP bridge → Tool Gateway (tool list and calls per run identity); mission tools become gateway tools.
3. Claude Code brain (session, streaming, permission prompts, command policy), the per-agent brain + model setting, the warning, the fallback to the model brain.
4. Missions move onto the engine; delete the mission-only execution path.
5. Persistent process per thread; Codex brain.

## Consequences

- One place for tools, approvals, audit, streaming and usage: a new tool or rule works for every brain and for missions at once.
- Missions lose their parallel execution path; the code gets smaller.
- People can run their agents on their own plans, at their own risk, with the model brain as a safety net.
- The engine extraction is a large refactor of `executor.ts`; it lands behind the existing tests with no behaviour change before any new brain is added.

## As built (blocks 1–6, 2026-10-17)

### Engine and brains (block 1)

- `packages/engine/src/brains/types.ts` is the one copy of the contract (`Brain`, `BrainTurn`, `BrainIO`, `BrainEvent`, `ToolResult`, `BrainTool`, `BrainSession`). The engine stays in `executor.ts` (`executeRun`, `EngineDeps`; `RunExecutorDeps` is an alias). Brains: `ModelBrain` (`brains/model.ts`), `createClaudeCodeBrain` (`brains/claude-code.ts`), `CodexBrain` (`brains/codex.ts`), registered by kind in `EngineDeps.brains` (`BrainFactory(agent, run, { mcpToken })`) in `apps/server/src/engine.ts`.
- One `run()` is one turn. The model brain yields `tool_call` without `executed`; the engine runs it through the Tool Gateway, appends the result and calls `run()` again (loop, limits, steering, pauses and cancel stay in the engine). The model brain reads the exact transcript blocks through its constructor (cache breakpoints, opaque thinking blocks); other brains get `BrainTurn.system` / `.messages` as text.
- **Computer brains end their turn with their tools.** Their `tool_call`s arrive `executed` (the bridge already ran and recorded them): they are shown, not re-run, and the turn ends at `done` (never re-sent). Executed calls are left out of the transcript, so it stays valid if the model brain takes over in a later turn. A turn that only ran tools and said nothing closes with "Done." (unless a bridged `react` made silence the answer).
- **Bridged side effects.** A bridged call's `data` (`reacted`, `artifact`, `missionLink`, `memoryUpdate`) goes through the same `absorbToolData` as the loop's calls: the bridge keeps it on the run (`transcript.bridgeEffects`, `memory.updated` published at once) and the engine takes it when it ends the turn (`takeBridgeEffects`), so the reply carries the cards and a bridged `react` closes the turn silently.
- **One reply placement.** `replyThreadOf` / `runWhere` (`run-tools.ts`) decide where a run's replies, cards and events go (flat for a top-level DM or routine trigger; else the thread), for the engine and the bridge alike.
- One implementation of tool access from outside the loop (`run-tools.ts`): `bridgeToolsFor` / `invokeToolForRun` (the runner bridge); the contract's `toolsForRun` / `executeToolForRun(deps, RunIdentity, call)` (executor.ts) and `BrainIO.executeTool` call them. The live tool chip is `invokeWithChip` for both. A gated call suspends the run like the loop (`suspendRunForTool`): it locks the run row and decides before posting anything — `running` suspends; already waiting on a call bridged in the same turn (two gated calls at once) joins the pending calls; any other state posts nothing, cancels the gateway's request and returns an error (`bridge.run_not_running`). After a computer-brain turn the engine reads the run's state: a bridged pause left it `waiting_*`, so the engine keeps the pending calls the bridge recorded, posts what the brain said and stops there — also when the brain then failed (no fallback, no failure). On the decision the engine resumes the run and the brain's session reads the result as text ("What a person decided on your waiting call: …"), since its `tool_use` lives in the session.
- Plan usage: each `usage { source: "plan" }` of a computer brain is recorded by `recordPlanUsage` (tokens on the run, agent and org, cost zero, `billed_to = plan`).

### Who thinks (blocks 3a + engine)

- Stored choice (migration 0061): `agents.brain` (`model` | `claude_code` | `codex`), `agents.brain_model`, `agents.brain_fallback` (default on); `missions.brain` / `missions.brain_model` override for a mission. APIs `GET/PUT …/agents/{id}/brain` and `…/missions/{id}/brain` (`brain-settings.ts`; `acceptPlanTerms` required to switch to a plan brain); web "Quem pensa" in the agent's settings and the executor's model in the mission's settings.
- `resolveBrain` (`brains/select.ts`) per run: the mission's brain and session when the run is its main session (`missionTurnFor`) → the agent's stored brain (`brainFor`) → availability on the agent's computer (`computerBrainUnavailable`: no computer, offline, commands off, runner below protocol 8, CLI missing or not logged in per `hello.executors`, Codex too old, a plan limit seen on this process until its reset).
- Session (2026-10-19): stored on the run (`agent_runs.brain_session_id`, so a pause resumes the same one). A new run takes the conversation's (thread, or the channel of a flat DM) last session only while it is recent (`SESSION_IDLE_MS`, 1 h) and its last turn read less than `SESSION_MAX_INPUT_TOKENS` (150k); else a fresh one, `brainSessionId(agentId, conversation:runId, kind)`, which gets the recent messages as its first prompt. A routine run always starts fresh. Before, one session per conversation was resumed forever: a half-hourly routine re-read up to 734k tokens per check. `resume` is a hint (plan usage exists for a run of that session); missions pass their main session (`main_session_id`, `repo_dir`). Model (`brainModelFor`): the mission's, else `agents.brain_model` only when the agent's brain is this same kind, else the brain's default (`sonnet` for Claude Code; Codex's own).
- Choosing a computer brain (`brainOptions`) requires the runner's `BRAIN_PROTOCOL` (8), the same check as at run time (`runner_old` below it); a mission's executor choice keeps its own check (`machineExecutors`).
- **No redo after tools ran.** A computer brain that fails mid-turn after tools already ran (bridge `tool_result` steps since the turn began, or calls it reported executed) is neither handed to the model brain nor retried: their side effects happened and they aren't in the transcript, so redoing the turn would run them twice. The engine posts what the brain wrote with `meta.brainInterrupted { brain, code, message, text, tools }` (the app adds the note in the person's language) and ends the run `done`.
- **Fallback, by what exists** (§5): the pre-check, a `limit`, or a brain error that is retryable or one of the unavailability codes (with no tool run in that turn) → if `brain_fallback` and the model brain has a credential (`ModelGateway.hasModelCredential`: catalog, provider and a key that resolves) the turn runs on the model brain and its replies carry `meta.brainFallback { from, code, message }` (the quiet note; it counts against the budget). Otherwise the agent posts once "… I'll answer when it's back" (`bodyCode: brain_unavailable`), the run waits in `waiting_input` with `transcript.waitingForBrain` (with a `waitId`) and `agent_runs.waiting_machine_id` (migration 0062, partial index; cleared by any transition out of `waiting_input`), and it is queued again when the computer comes back (`resumeRunsWaitingForMachine` from the hub's `online` hook: one job per wait, dedupe key `…:brain_back:{waitId}`) or at the plan limit's reset.
- **Computer just gone** (added 2026-10-30). A computer gone for less than the outage grace (`TASK_OFFLINE_GRACE_MS`, 2 minutes since its last sign of life: its runner dialing again, our own restart) is usually back within seconds. A run whose first look finds it offline waits for it before anything else, up to 30 s (`COMPUTER_BLIP_WAIT_MS`), asking every second. The run stays `running` (its heartbeat and its job's lease go on), so the apps show it working as usual, and nothing is posted or stored: no note, no `waitingForBrain`. Back in time, the turn goes ahead. Still away, the fallback or the note and the wait follow as above. A cancel or a stop ends the wait at once. A run back from waiting for its computer (its "back" job, a message to it, the end of the drop grace) doesn't wait again, and a computer gone longer is an outage, said at once. As no run waits during that window, "Computador desconectado" keeps its grace for these blips too. The waiting card, that notice and a routine's panel offer "Trocar computador" only where people connect their own computers (`computerEdition` says `selfhost`, known from boot through `auth-config`'s `workspaceComputer`): a Cloud workspace has one computer, and while the edition isn't known nothing is offered. Before, a computer gone for a few seconds got the note at once, with its waiting card and a switch to nowhere on the Cloud.
- **Busy computer** (added 2026-10-27). A turn the runner refuses for room (`no_slot`, ADR 0025 §5, admission) or at its request ceiling (an older runner's `busy`) is the brain error `busy`, for Claude Code and Codex. With a model credential the fallback stays as for any computer that can't answer. Without one the run waits as for an offline computer (`waiting_input`, `waitingForBrain` with code `busy`, `waiting_machine_id`, the same one note per place), but an online computer sends no "back" signal, so a job asks again every 15 s (`COMPUTER_BUSY_RETRY_MS`, dedupe key `…:room:{waitId}`). Each look is a job of its own, so the run's job keeps its tries; it says nothing in the conversation until a turn starts (no "thinking" every 15 s), and the run's trail gets one step per wait. The note said "My computer is busy with other tasks right now. I'll answer as soon as it's free." (`chat.body.brain_busy`, still how older notes read); since 2026-11-02 a wait for room posts nothing for 10 minutes and the note is another (addendum "Calm waits"). A routine's run waits quietly, without the "waiting for the computer" notification. Until 2026-11-02 a run failed with `computer_busy` 30 minutes after its first refusal (`run.computer_busy`, still how those runs read in the chat, Atividade and Rotinas); since then a wait for room never ends a run (addendum "Calm waits"). Before that, `busy` retried on the job's backoff and failed `gave_up` after about 2.5 minutes.

### The runner MCP bridge (block 2)

- Identity: `run_tool_tokens` (migration 0060), SHA-256 of `agr_…` tokens bound to org, agent, machine and a run or a mission task (`issueRunToolToken` / `verifyRunToolToken` / `revokeRunToolTokens`). The engine issues one per computer-brain turn and passes it in `brain.turn.mcp.token`; tokens are revoked when the run stops or waits. Verification checks the hash, the machine holding the socket, expiry, and that the run is `running` (a waiting or ended run is refused) or the task has not ended. Mission tasks get one at `startMachineTask`.
- Protocol 8: `mcp.call` carries `token`; `mcp.list` → `mcp.tools` answers `tools/list` with the run's Tool Gateway list (`toBrainSchema` inlines `$ref` and flattens top-level `oneOf`/`anyOf`/`allOf`). Without a token (runners up to protocol 7) the legacy mission path stays.
- `run-tools.ts`: `bridgeToolsFor` (runs and mission tasks), `invokeToolForRun` (error codes) and `suspendRunForTool` (approval / question / secret cards, or a mission tool's own wait; the pending call is marked `bridged`).
- Mission tools are gateway tools: a task's (`createMissionBridgeToolSource`, its own gateway, `permission_prompt` included); a computer-brain run in its mission thread gets the main session's mission tools (`createMissionToolSource`) plus `get_context`, `upload_artifact` and `start_task` (`createMissionRunToolSource`, listed before the sandbox tools so they win the `start_task` name for bridge calls).
- `permission_prompt` works for runs: in the agent's open mission thread it is the mission's command card flow keyed by the run (no task; `PromptAsker`); elsewhere `runPermissionPrompt` (deny list refused, plain reads allowed, and what code allows when the agent has the sandbox scope; the rest denied with what to do instead: nothing waits for a person outside a mission).
- **A permission check reads as its command** (added 2026-10-30). Each command Claude Code or Codex asks about is a `permission_prompt` step, and the bridged chip carried no label for bridge calls, so a long run showed a column of the same "Consultou o permission" line. Its label (`toolDetail`, on the bridged chip and on the recorded step) is the command: Claude Code's own one-line `description` when it gave one, else, built from the already masked line (`redactCredentials`: also an address's user and password and the value after a secret-named option such as `--password`), the first program and its main argument: the words before its first option, else its first path or web address, never another word after an option (it could be that option's value), a web address as its site and path. The chip and the step also carry the whole command as one line, masked (`command`, at most 1000 chars), which the line opens on. A refused command ends its chip `failed` with the policy's reason (`why`, only from a `deny` answer: an error's text could hold anything) and its code (`refusal`: every `deny` the server answers carries one, `person`, `expired`, `never`, `secret`, `plan`, `tooMany`, `off`, `team`, `unknown` or one per `forbiddenReason`, `forbiddenCode`), which the apps say in the person's words (`chat.work.refusal.<code>`, `toolWhy`; the reason's first sentence only for an answer with no code). One waiting on a person ends it `held` with its request (`requestId`). The runner asking again about it (`request_id`) gets no chip and no step on the task's card (`promptPoll`) and is left out of the reply's tool count (`meta.work.steps`); once the person answers, an end with that `requestId` and no `toolUseId` settles the line that waited (refused when they said no), live and in a saved trail, and a run whose last call waits on a person never reads as quiet (`isQuiet`). The task's card reads the checks' answers too: a step refused or still waiting carries `outcome` (`refused`, `waiting`) and reads "Recusado: …" or the stopped verb, never "Rodou". The apps say "Rodou: …" / "Ran: …" and "Recusado: …" / "Refused: …" with the reason under the line, and fold the same line in a row, the task's card too ("×3" with the last time); a failed or waiting call stays a line of its own, live and saved. Our own tools whose first word read like an app (`hand_off`, `git_clone`, `open_pull_request`, `record_findings`, `complete_mission`, `request_permission`, `request_folder_access`, `request_secret`, `use_tool`, `follow_up`, `cancel_follow_up`, `desktop_*`, and `pg_<slug>_*` when no connection label comes with the event) have their own words.

### Claude Code and persistent processes (blocks 3b + 5)

- **Protocol 8, one bump** (`MACHINE_PROTOCOL_VERSION = 8`, `BRIDGE_PROTOCOL = BRAIN_PROTOCOL = 8`, runner 0.8.0): `brain.turn { runId, kind, session: {id, resume}, cwd, model?, system, prompt, mcp: {token}, keepAlive?, personalMcp?, permissions? }`; the runner streams `brain.event { runId, event }`, then `brain.done`, and the result repeats the final event. The hub publishes the frames on `brainTopic(runId)` for whichever replica runs the turn.
- **Runner** (`apps/server/runner/brain.ts`): `claude -p` with stream-json in and out, `--resume` or `--session-id`, `--model` (+ `--fallback-model sonnet` under opus), `--append-system-prompt-file`, our MCP bridge (`--strict-mcp-config` unless `personalMcp`), and the command policy (`--settings`, `--permission-prompt-tool`, deny list). Missions pass their policy (plan before Start, work after; branch prefix; allowed commands). Only our bridge's tools become `tool_call` events (`executed`); usage is `plan`; a rejected rate limit is `limit{resetsAt}` then `error plan_limit`; login failures `not_logged_in`.
- **One process per (agent, session)**, stdin open, closed after 3 idle minutes, at most 1 kept per agent (changed 2026-11-02 from 10 minutes and 3 processes, since idle CLIs filled 8 GB computers). On a person's computer one runner serves every agent, and one agent's turns never close another's warm process. A person's own `brainIdleMinutes` and `brainMaxProcesses` in the config still win. The least recently used idle one closes for a new conversation. When every process is busy, a turn still gets its own process. Before, it ran one-shot and couldn't take live messages. As turns end, the extra ones close, least recently used idle first. So an agent still works on several conversations at once, and only the cap stays warm afterwards. A process holding the agent's work is never closed for being idle, for the cap, or for room (ADR 0025 §5). That work is a task in the background, such as a dev server or a watcher, or a turn of its own. Those processes are looked at again later. A background turn (`keepAlive: false`) and a retry after a crash run one-shot and end with their turn. ## Addendum (2026-11-02): calm waits on a shared computer

A workspace ran fifteen agents on one 8 GB computer. One message mentioned twelve agents at once, and they mentioned each other back: the runner admitted the turns its memory floor allowed (ADR 0025, admission) and refused the rest `no_slot`. Each waiting run then posted its own "my computer is busy" note, which reads as the agent refusing. A deploy dropped the computer's socket for seconds, and every waiting run posted "offline", then "busy" again, and each offline note later showed as its own "<computer> is back" card. One agent had six runs waiting, one per mention. A person's direct message waited behind agents talking to each other. The runner is unchanged (no protocol change): what changed is how the engine waits and what the chat shows.

- **Waiting for room is a live state, not a chat line.** A `busy` wait posts nothing for `COMPUTER_QUEUE_NOTE_MS` (10 minutes) after `roomWaitSince`. A run still in line then posts one note, "Still in line for the computer. I'll answer as soon as it has room." (`brainUnavailable.long: true`, worded `chat.body.brain_queued`). Nothing is dropped: a run in line keeps its place until it runs, however long that takes. Long work (ADR 0121) wakes through agent turns on the same computer, so a limit could end it halfway; the `computer_busy` failure after 30 minutes (`COMPUTER_BUSY_WAIT_MS`) is gone. `roomWaitSince` survives only a blip: a quiet `machine_offline` wait (within the outage grace, below) and a turn dropped before the computer said or did anything (a deploy as the turn went out), so a deploy keeps a run's place and its clocks. A real outage, any other wait or a turn the computer took ends it: otherwise the 10-minute note and its place in line would count the time the computer was gone as time it was busy.
- **A computer just gone waits without a word.** A `machine_offline` whose computer was last seen less than `TASK_OFFLINE_GRACE_MS` (2 minutes) ago parks quietly (`waitingForBrain.quiet`), with a look queued at `lastSeenAt` + the grace (`…:offline_note:{waitId}`). Back before then, `resumeRunsWaitingForMachine` resumes it and that look finds another wait. Still away, the next look posts the note. A quiet wait doesn't make the computer an outage (`listMachineOutages` skips it like `machine_dropped`), and a routine's run doesn't announce it.
- **At most one note per place.** `noticeAlreadyPosted` and `brainNoticeIn` are gone. Under an advisory lock on the place (`waitNoteSaid`), an offline note is skipped when a note for the same computer is already in the same channel and thread since the computer was last seen (one per computer, place and outage, whichever agent posted it). Any note is skipped when the agent's last message there is already a note (one per agent and place until it answers). The apps hide a note once the same agent wrote anything later in the same timeline or thread (`supersededBrainNotices`, web and phone): the "<computer> is back" card is that note, so it goes too.
- **The person's message shows the wait.** Receipts carry `handled[].computer` (`queued`: in line for room; `away`: waiting for the computer to come back), and so do `agent.run`, `run.finished` and `message.handled` (`computer`). So does `agent.run.steered` when the message went into a run waiting for its computer, so the live view matches a reload. The apps word them `receipts.queued` / `receipts.away` instead of "waiting for your answer". The agent's line says `queued_computer` ("In line for the computer") for a `busy` wait.
- **One waiting run per agent and conversation.** In a channel's main timeline, a mention by an agent (`startOrJoinRun`) and a person's message (`insertMessageWithRuns`) join the agent's in-channel run that waits for its computer (`waiting_input` with `waiting_machine_id`), as they already joined a queued or running one. `mayJoin` still decides who may join whose run. A Continuar (`granted`) never joins it: it starts its fresh stretch. An agent's message raises the run's hop to its own depth (`greatest(hop, message.hop + 1)`; not in DMs, where joins were already allowed), so the hop limit still holds for the run's replies. What the run's next turn would have read when it parked is kept (`transcript.continued`): the trigger and joined messages, a person's decision on a bridged call (`resumeText`, whose pending calls are already gone), and a turn cut by a dropped computer. The next claim reads a saved `continued` before it rebuilds a cut turn's prompt.
- **People first, in order (`computer-queue.ts`).** The engine keeps the computer's line without a table: runs `waiting_input` on `waiting_machine_id` with code `busy`, people first (`transcript.roomPeople`: a person's run at hop 1 that no routine started, or any run a person's message joined while it waited, `frontOfLine`: from `afterSteered`, and from `startOrJoinRun` for a message the router or a hand-on brought, which no steering follows), then by `roomWaitSince`. Only the head asks the runner again (`roomHead`); any other run's look queues the next one and returns before it claims (one indexed query, no context, no runner call). A turn that ran on the computer asks the head at once (`kickRoomQueue`, `…:room-kick:{waitId}:freed`).
- **Paced fan-out (`roomGate`).** Before a run's first computer turn of a claim, under a lock on the computer, it is behind when a run waiting for room ranks ahead of it, or, for agents' work, when another running run sent a turn to the same computer less than `ROOM_ASK_SPACING_MS` (3 s; 10 s until 2026-11) ago (`transcript.roomAsk`). Behind, it parks as a `busy` wait (`queued`: never the model fallback, never sent to the runner) and looks again when the spacing is over, or, behind another run in line, after `ROOM_BEHIND_RETRY_MS` (10 s), a fallback: the line moves by kicks. Otherwise it records its ask and asks the head again once the spacing is over. A person's turn never waits for the spacing. The runner's memory floor still decides every turn: an out-of-memory kill would take every session on the computer, so only a locked-down turn and a person's reserved slot go under it, each to a floor of its own, and the spacing lets the runner's memory reading show each CLI's real size instead of the 0.6 GB estimate.
- **Limits.** Runs that come back together from a blip (`resumeRunsWaitingForMachine`) aren't in the line while they claim (`running` rows don't carry the computer), so the first to reach `roomGate` goes whatever its `roomWaitSince`; the agents' spacing parks the rest in order, and the memory floor still decides. Nothing holds memory back for people while long agent turns run: a person's turn takes the reserved slot if the computer has room for it, or else waits at most for the next turn to end, then goes first. A later turn of a run already working isn't gated.
- **The line, visible (`computerQueue`, `GET /api/app/organizations/{orgId}/machines/{machineId}/queue`).** Any member of the workspace reads a computer of that workspace: `working` (running runs whose `roomAsk` names the computer, from `roomAsk.at`) and `waiting` (the line in `roomHead`'s order, `position` 1 = next), each with `agentId`, `where` (`channelId`, `threadId`) and `purpose`, what the turn is for in structured words, never its content: `person` (`userId`), `agent` (`agentId`, who asked), `routine` (a background run or a routine's call) or `work` (long work, ADR 0121). The runner's live memory isn't known to the server (`pong.load` is a day's average), so the snapshot carries none; a non-empty line means the computer is full.
- **Estimates (`estimateQueue`, pure; `typicalTurns`).** A turn's typical duration is the median of the agent's latest 20 finished computer runs (from `roomAsk.at` to `finishedAt`, last 14 days, at most 300 runs read, cached a minute per process), else the workspace's median over those, else none. A running turn's `estimatedEndAt` is its start plus that, never sooner than 30 s from now (`QUEUE_END_FLOOR_MS`). The line's `estimatedStartAt` simulates the slots: each running turn frees one at its expected end, the next in line takes the soonest (unknown ends last, the longest running first), an agent's turn starts at least `ROOM_ASK_SPACING_MS` after the previous ask, and then holds the slot for its own typical turn. A slot with no basis frees at an unknown time, so that turn and every one after it gets null. `after`: for the head, the running turn it waits for (the apps say "once Ada finishes"); behind it, the agents ahead in line.
- **Realtime.** `computer.queue` (`{ machineId }`, an org broadcast, `publishQueueChanged`) only when the line changes: a run joins it (not the head refused again), a run that never waited is admitted (after the transcript holding its `roomAsk` is saved, so the refetch lists it working), the head admitted from the line takes its turn (the brain's first event: the runner may still refuse it, and a refused re-ask sends nothing), a computer turn ends, a run that asked the computer ends (`finished`), a run in line or working is stopped (`stopRun`) or moved to another computer (`moveAgentsFromMachine`), and a person's message sends a run to the front (`frontOfLine`: its job carries `line`, told once the move is committed). The apps refetch (`keys.machineQueue`).
- **Routines in line keep their place.** A routine's run waiting for room (`busy`) is not superseded by the next slot (`checkPrevious`): the slot gives way (`previous_waiting`) and nobody hears of a stall. Only an outage wait is replaced and notified, as before.
- **An ask from the line changes nothing for anyone reading.** The head asks by claiming its run, which keeps `waiting_machine_id` while `running` (`computerWaitOf`, `computerWaitSql`). The line, the receipts, `active-runs` and the agent's status read that as still waiting until the computer takes the turn (`leaveLine`, which also tells what the ask held back: `agent.thinking`, `message.claimed`, the line). Read as gone, the waiting row went away at every ask, and a person's message starts one the moment the apps refetch the line. A run picked up `running` with its machine kept (the worker died asking) asks again, and a first turn starts the run's clock (`startedAt`) when it leaves the line: minutes in line are no minutes of work.
- **One wait per run, at the end of the conversation.** `conversationWaits` draws it from the receipts, however many messages went into the run; the line only adds its place and estimate, so a read that lacks the run takes nothing away ("Waiting for the computer"), and a run with a live row has no wait, whatever a stale receipt says. Back after missing events, a list of active runs asked after a run was heard to stop brings its row back (`reconcileRuns`): it stopped to wait and went on. A status reply or a fast reply during a wait says so (`talker_status` with `wait`, `meta.talker.waiting`): the minutes are the wait's.
- **In the apps (`@agenteschat/client/lib/computer-queue`).** `queueView`, the live row (`queueLiveText`), each row's purpose, place and time, the header button, the outage card's pill (`awayText`) and the fan-out strip under an agent's message that called several agents (`fanOutOf`: from the message's receipts, `runOf` matched to the line by run id, agents not started yet counted in line), worded under `queue.*` and `receipts.queuedNext`.

- **Another account.** Every way it can think, in one list (`useBrainState`): the accounts on its computer of every plan (Claude to ChatGPT is another row), that computer's own sign-ins, the workspace's keys (whoever may pick one; anyone else gets the API as the agent has it), and a plan that would move it to another computer ("Vai para o MacBook", as `homeFor` decides). "Em uso" first, then the person's, the keys, each other owner's, those at their limit last; past three the three with most room and every one under a search (`HaveList`, shared with Connect). The one with most room comes picked. Someone else's plan says at the foot that its owner hears of it. A row that needs a sign-in (one more login of an account, one signed out) opens it in the dialog, and the switch saves once it signs in. "Conectar outra IA" opens Connect for the agent.
- **For the others on it.** When the account in use thinks for all of its owner's agents there and the one picked does too, two cards ask whom it is for ("Só a Ada", "Todos nesta conta"); for all, each agent is moved by the server's own rules, keeps its own model, and one it refuses is named on the last screen.
- **At its limit it opens on the way out.** The agent sleeps under a night sky, the screen says when the plan is back ("Claude · Max volta sábado às 18:00") and offers the owner's accounts with room (`limitOffers`); "Esperar" closes. Another account brings the day back.
- **Each screen saves its own change.** The model (Automático first, each model with its line, grouped by maker, what it needs from the plan's account under the list); "Mais opções" (effort, speed and context as lines that open under themselves, the fallback to the API, "Atende outras pessoas" with its terms, paid extra usage, the computer where several run it, "Usar em outros agentes", ADR 0094) saved by "Concluído". There is no global "Usar".
- **"Pronto", and "Desfazer".** After a switch the last screen says what thinks now ("A Ada agora pensa com Claude 2 · Max") and that what was under way goes on with it. "Desfazer" puts back what each agent had: its brain, account and model (and its computer and key where the switch changed them), read before the switch for the others. An account taken from another agent stays with this one.
- **Someone else's agent.** An admin on an agent another person owns picks among that owner's accounts the server lets them use and the workspace's keys; the owner's other accounts show under their name, not to be picked. Signing in and "Conectar outra IA" stay the owner's: there is no sign-in in the dialog for anyone else. A sign-in needs the agent's computer, so with none a row that asks for one can't be confirmed.
- **Opened on a screen.** A link can open it past its first screen, which "back" leads to: `?sec=brain&brain=model` (or `more`, `switch`) on the agent's page. The notice that a model left its plan's list ("Escolher outro modelo") opens it on the model. A screen the person can't change opens the first one instead.
- **Motion.** Screens slide in from the side they come from, the dialog's height glides between them, bars fill as they show, a new mark comes in where the last stood and the trail lights after a switch; with reduced motion nothing moves.
