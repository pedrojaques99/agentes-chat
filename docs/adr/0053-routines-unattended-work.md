## Context

Routines are agents working while nobody watches: Theo's daily analytics and a 30-minute review check, Lisa reading a customer inbox every hour, Ada doing the issues assigned to her and opening PRs, Atlas checking Sentry every hour. In production almost every routine runs on Claude Code on someone's Mac, not on the API. The delivery model built for chat (a silent background run that speaks only through `hand_off`, which wakes a normal run of the same agent that tells people in its own voice) is right and is kept.

An audit of the code (lifecycle, safety, product), of `feat/agent-runtime`, of OpenBot and OpenMausBot, and of how the engine shares one base across brains found:

- **Authority.** A routine's trigger is written as its creator, so every "who asked?" check finds the creator: an unattended run reading a hostile email can rewrite its own routine, post in other channels, DM people and drive other agents with the creator's authority. Only `ask_user` and `react` are refused.
- **Computer brains.** Routine runs get the full "work" profile on a person's Mac. Codex runs with no approvals and no deny list (`approvalPolicy: never`, network on); Claude Code's deny globs can be bypassed and secret files read. Background runs silently fall back to the API brain when the computer sleeps.
- **The ledger.** `routine_runs` closes only on a final answer (564 rows stuck in `started` in a week); stops, failures, deploys and cut-off computer turns leave it open, and some of those paths post into the conversation.
- **Firing.** Nothing stops a routine's runs from overlapping or stacking approval cards; a computer that sleeps leaves an old run waiting and skips every later slot silently (49 skips in a week, nobody told); failures notify on every slot and never pause; `issue.created` routines can trigger themselves; events are neither deduplicated nor coalesced; there is no minimum interval.
- **Noise and privacy.** Every firing writes a line into the conversation that counts as unread for everyone; any member can read every routine's records (customer emails included); notices meant for one agent read as another's own; the agents' DM mixes exchanges done for different people.
- **Engine.** 22 brain-kind branches in `executor.ts`, two paths that post pause cards, the agent's stored brain read where the run's real brain matters, computer sessions keeping a stale system prompt, and no test that runs the same scenario on every brain; evals cover only the API brain.

The product decision stands: a routine thinks with its agent's own brain (Claude Code, Codex or the API), never forced onto the API.

## Decision

### 1. One gate for who is behind a run

`authority.ts` decides, for every brain and every tool, who a run acts for:

| Kind | When | Acts for |
|---|---|---|
| `person` | A person asked, directly or through agents (an agent's message counts for the person behind the run that wrote it; an answer to another agent's question for the person behind the asking run) | That person, within their permissions and the agent's scopes |
| `routine` | A routine's background run | Nobody. Its creator set it up and stays accountable (notifications, approvals) but is never "behind" it; what it may do comes only from the routine's access level |
| `unattended` | No person at the root: the run a routine's report wakes, a note from another agent, an agent's own message, anything they start | Nobody. It reads and talks where it is |

Only authorship and server-set links are followed (a message's run, a notice's `refs.runId`), never message metadata alone. A person writing into an unattended run while it works (`Transcript.steeredBy`) puts them behind it from then on. Every existing "who asked" helper (`requester.ts`, `dispatch.requesterOf`, the ones in chat, schedule, artifact, secrets, team, agent-actions and notification code) delegates to it. `accountablePerson` is whom approvals, questions and failures go to: the person, else the routine's creator, else the agent's owner.

### 2. What each kind may do: one policy table in the Tool Gateway

`tools/run-policy.ts` maps (authority, routine access) × tool to allow, refuse (with a reason the model reads) or approve (forced approval card). The gateway enforces it at listing (refused tools aren't listed) and at every call (defense in depth), so it holds for the API brain and for Claude Code and Codex, which reach our tools through the MCP bridge.

- **Routine runs, any access:** refused, with "put it in hand_off; the people decide": `post_message`, `send_dm`, `share_artifact` to others, `react`, `ask_user`, `schedule_reminder`, `cancel_reminder`, `create_routine`, `update_routine`, `delete_routine`, `run_routine_now`, `ask_agent`, `tell_agent`, adding agents or people to channels, `request_secret`, `request_permission`, `request_folder_access`. A routine never manages routines.
- **Routine, access `read` (the default, "Só olhar e contar"):** reads only (built-in reads, connector tools classified as reads, memory/wiki/issue/Drive reads, search) plus `hand_off`. Writes are refused ("this routine only reads: hand off what you'd do").
- **Routine, access `act` ("Pode agir"):** also internal changes people can undo (issues, memory, wiki, Drive files, `git_clone`, work on its own `agentes/<handle>/` branches and PRs). Every write to a connected app becomes an approval card, whatever the agent's own "send without asking" settings say. Sensitive actions (merge, deploy, rollback) are approvals as always. *Amended 2026-10-31:* the exact call a person approved ahead for this run (`schedule_action`, ADR 0015 addendum) goes out without a card, until its time plus a short grace; merge, deploy, rollback and the rest of the never-for-good list can't be approved ahead.
- **Unattended runs:** reads, the reply where they are, `react`, `pass`, issues and memory with receipts and Undo; connector writes become approvals; refused: posting elsewhere, DMs, routines, reminders, consulting or telling other agents, secrets and permissions. A run a routine's report woke works within that routine's access (`routineAccess`, from the brief its run handed off with): the report of a routine that only looks wakes a run that changes nothing itself and proposes (the issue it would open, with a title); a person's go-ahead puts them behind it. Connector writes still become approvals, asked with the tool itself and its reason, never in words.
- **Person runs:** unchanged.

The mail taint generalizes: any routine or unattended run that sends mail gets a card.

*Amended 2026-10-31 (routines reach agents):* the owner decided that a routine may post and message without an approval step when the person who set it up asked for it, which is what access `act` says. A routine's own work had no way to reach another agent: a sales agent's routine set to nag a dev agent until its pull request was ready could only hand off, and its run told people the tool to message other agents was down. Now a routine set to act also reaches other agents and posts where its creator can, through the tools any run uses, each holding it to its creator's rooms and agents (`routineCreatorOf` in `requester.ts`):

- **`tell_agent` and `ask_agent`:** only agents its creator can talk to (their audience and `talk_to_agents`, as for a message of theirs), with the consultations' own rules (no cycles, their chain limit, the same note once an hour).
- **`post_message`:** only in a channel its creator can post in now (`personCanPost`: in the workspace, holding `post`, a member of the channel), and in a private one only when the agent is in it too. Files only from where it posts: never through its creator's access to a DM or a private channel. An @mention there wakes only agents its creator can talk to (`dispatchMentions`).
- **`send_dm`:** only to its creator, in their DM with the agent.
- **What stays refused, any access:** reactions, questions to people, reminders, routines (a routine never creates, changes or runs one), channels, secrets and permissions. The tools' own approvals hold: a sensitive or outside action asks a person, on a card where the routine reports.
- **A routine set to only look and tell** keeps its limits: the four tools aren't listed, and a call is refused with why (`routineReachReadOnly`: its creator set it to only look and tell, and a person can set it to act). The routine block says what each level reaches.
- **Nobody is behind what it starts (§1):** the agent its note, question or mention wakes works `unattended`, and the routine's run never acts as its creator, who stays accountable.
- **Loops stay held:** what a routine's run starts counts in its stretch (ADR 0089) as work nobody asked for, 10 runs (`STRETCH.unattendedRuns`): its brief, the stretch's first message, counts like its report does. The pause card goes where the routine reports (a refused `tell_agent` or `ask_agent` too, never its room) and is for its creator, who may Continuar. The per-routine limits of §6 hold as they were (one run at a time, at most every 15 minutes, 20 active per agent) and no routine starts another, so two routines nagging each other's agents open one bounded stretch per firing each.
- **Where answers go:** a note's reply or a question's answer that comes after the routine's run ended goes where the routine reports and wakes the agent there (`deliverNoticeToRun`); while the run still works, it reads it at its next step. A consulted agent's cards for a routine's question go where the routine reports too (`consultationOrigin`).

### 3. Computer brains follow the same authority

`apps/server/src/engine.ts` picks the permission profile per turn from the run's authority: `plan` (read-only: no edits, read-only shell, no web fetch or search, no project settings files, our MCP tools only) for routine runs with access `read` and for unattended runs; `work` for `act` routines and person runs. Codex gets the matching profiles: a read-only sandbox without network for `plan`; for `work`, `approvalPolicy: "untrusted"` with every command approval answered by the same command policy Claude Code's permission prompt uses (deny list, read-only allow, forbidden reasons). The command policy is hardened for all runs: secret paths are refused to every read tool our policy sees (one list builds the server's check and Claude Code's own `Read` deny rules, in the home folder and in any project), deny rules match normalized arguments (`gh -R`, `git -c/-C`, `refs/heads/<default>`), interpreter one-liners (`node -e`, `python -c`…) and `gh auth token` are never auto-allowed. Background turns don't keep their computer process alive. An older runner that can't honour a profile fails the turn with `runner_outdated` instead of running with more power: every Codex turn and every Claude Code `plan` turn need protocol 16 (an older runner's plan reads secrets and loads the project's settings files).

In a mission's thread the mission keeps its own profile for its own work, but a run a routine's report or another agent's note woke there gets `plan` like anywhere else.

Codex runs the commands it considers safe (`cat`, `grep`, `ls`…) without asking, inside a read-only sandbox that can read any file the computer's user can: on Codex a secret file can be read even in `plan`, so what holds there is that it can't leave. Its sandbox has no network; every tool call of a run nobody is behind is refused when it carries a credential by its format (keys, tokens, private keys; `tool.credential`), on every brain; and what such a run posts, and a routine's report, have credentials masked. A per-turn Codex permission profile with denied paths (Codex has `default_permissions` and `[permissions.<id>]` profiles) is the next step.

*Amended 2026-10-30:* the command policy is one policy for every path that runs a command on a computer, not only the brain's own commands: Claude Code's prompt tool and Codex's approvals, `run_code`, skill scripts (`run_skill_script`) and background tasks (`start_task`: a shell task's command, and every command of Claude Code inside one, a mission's items included). Routines and missions run commands only through those, so they follow it too. Before, a background task ran its command unchecked, so a push the brain's own terminal had held could go out through one.

- **What waits for a person.** Merges, deploys, rollouts and rollbacks, removing infrastructure, publishing, `gh api`; a push to the remote's default branch or to a branch the repository marks protected; a force push to a branch that isn't the agent's own; deleting a remote branch; `--all`, `--mirror` and `--prune`. A printed token is refused like any secret, never asked. Everything else is ordinary work: any other push (a pull request's branch included), a force push to the agent's own branches (`agentes/<handle>/`, a mission's prefix), a dry run.
- **How the computer decides** (`apps/server/runner/command-gate.ts`, the rules in `packages/adapters/src/command-policy.ts`). It reads each push of the command the way git reads it (`cd` and `git -C` before it, wrappers, a shell's `-c` script, refspecs with `heads/<branch>` as git's short `refs/heads/<branch>`, `:` as every branch both sides have, `HEAD`, and every option to the last, which wins as in git: `--dry-run --no-dry-run` pushes), then asks git in the repository it runs in: the branch checked out and where a bare push goes (`@{push}`; `push.default=matching` has no single target), the remote's default branch from `refs/remotes/<remote>/HEAD`, else the remote's own `HEAD` (`git ls-remote --symref`, at most 10 s), and the protected branches from `git config agentes.protectedBranch` (repeatable, `*` matches anything: `release/*`). Nothing assumes `main`: where `develop` is the default, a push to `main` is ordinary. When it can't tell, the push waits: no repository, a remote it can't reach, a detached `HEAD`, a line it can't read plainly such as `git push origin $BRANCH`, an option it doesn't know (an abbreviated one included), inline config that changes where a push goes (`-c` or `--config-env` with a `push.*`, `remote.*`, `branch.*` or `url.*` key, or an include), an inline alias, a push another program runs (`xargs`, `eval`, `sudo sh -c '…'`, text piped into a shell, `git submodule foreach`, `rebase --exec`), a bare push or `HEAD` after a checkout in the same command (`git checkout main && git push`: git is asked before the command runs, on the branch checked out then), code in another language that runs git push. It also reads the script an `<interpreter> <file>` command runs (`run_code` writes its code to one): a shell script as commands, other code by the commands it spells out.
- **The refusal names exactly why and what to do**, never a generic list: "This push goes to the default branch main: a person approves it first. To ask them, run the same command with run_code, with why set to your reason: it waits for their decision in the chat. Or push to a branch of your own (agentes/ada/…) and open a pull request." A force push says it is one and to push without force; a deploy says it is a deploy. Inside a background task nobody can approve anything, so it says to stop and say so in the result.
- **Asking is the approval card.** `run_code`, `run_skill_script` and `start_task` take a `why`; a call that carries one is an approval in the chat (ADR 0015, amended 2026-10-30), a routine's where it reports, with its origin. The approved call reaches the computer with `approved`, and that exact command runs. The runner's refusal is `approval_needed`, and nothing ran.
- **Claude Code.** Pushes leave its deny rules and become `ask` rules (`PUSH_ASK_RULES`: any command with `git push` in it, or git's global options before `push`, so `git --no-pager push`, `/usr/bin/git push`, `env git push` and `sh -c 'git push'` too), which outrank allow rules, the computer owner's own and a project's too (a work turn loads the folder's `.claude/settings.json`), so every such command reaches our prompt tool, which reads where it goes and allows at once one that only reads (`grep 'git push'`). The allow rules for the turn's own branches are gone: the prompt tool itself allows a push to the agent's own branches when it is `git` alone, with no wrapper, no shell around it and no option that runs a program. A Claude Code task outside a mission gets the deny list, the `ask` rules and the prompt tool answered on the computer alone (`AGENTES_MCP_TASK=local`): an ordinary push alone goes through, a held one is refused with why, and anything else the computer can't allow by itself is refused, as `-p` always did. The server no longer refuses push spellings (`main`, `master`, refspecs with `:`): only the computer knows the repository, and an older runner keeps its own rules.
- **Not reached yet.** Codex background tasks: `codex exec` can't ask, and the runner doesn't see their commands before they run, so their sandbox (workspace writes, with network) is the limit, as before. A terminal typed into on the agent's desktop (ADR 0062). A git-level guard (a `pre-push` hook) or running those tasks on Codex's app-server, as brain turns do, would reach them. Reading command lines stays what it was, not a security boundary (ADR 0030): past the script a command names, nothing is followed (a `make` target, a package script, a program that runs git itself). In a Claude Code turn a command is read only when it reaches our prompt tool: the turn's allow rules run scripts unread (`node`, `python3`, `make`, package scripts), and a project's own settings can allow more (with `Bash(git *)` there, `git -c alias.p=push p` runs without it). Config set beforehand isn't read either: an alias (`git config alias.p push`), `remote.<name>.push` or `remote.<name>.mirror`, a branch made a symbolic ref to the default one.

*Amended 2026-10-31 (ADR 0024 addendum of the same day):* through our git proxy the server decides what a person may approve for git: it refuses deletes (`delete_branches` asks a person and deletes on GitHub), the default and protected branches (a pull request, and merging asks a person) and every force push, and lets the agent push to someone else's existing branch once a person approves `request_branch_push`. So the computer doesn't offer a `run_code` card for what the proxy would then refuse.
- **Through the proxy** (`RepoFacts.viaProxy(remote)`: every push URL of the remote, from `git remote get-url --push --all`, which applies `insteadOf` and `pushInsteadOf`, is one of our `/api/git/<org>/<connection>/` URLs; a URL given as is is read with `git ls-remote --get-url`, and unknown when any `pushInsteadOf` is set; unknown counts as no), the holds above become `never`, each pointing to the server's way: deleting to `delete_branches` (the same `DELETE_BRANCHES_POINTER` the proxy prints); the default or a protected branch, `--all`, `--mirror` and `--prune` to a branch of its own and a pull request; a force push to pushing without force. What git can't tell stays a person's call, as before.
- **`never` outranks the rest.** A command with a `never` push never runs: `approvalNeeded` puts it before the deny list and the pushes a person could approve, so no approval lets it through. The runner answers `not_allowed` for it (`exec`, a shell task's `task.start`), with a person's `approved` too, and the prompt tool denies it; the server shows that refusal as it is (`policyRefusal`: it ends with `NO_TERMINAL_COMMANDS`), "Not run: …" with `command.not_allowed`.
- **A push alone through the proxy to someone else's branch** runs on the computer, as one to the agent's own branches does: the proxy decides it with the grant, so a mission's command card doesn't ask before the grant's card does.
- Not through the proxy, nothing changes: `run_code` with a `why`, a card, then the command runs with `approved`. A URL made to look like the proxy's only makes the computer stricter, except that plain push, which this policy already lets through without asking.

### 4. The routine room, the brief and where a routine delivers

A routine fires a background run in its own room: an agent-only conversation per routine (`routineRoomKey`), hidden from people, from search for other runs and from agents' channel lists. The trigger is the routine's brief, written by its creator, with `meta.routineBrief` (`RoutineBrief`: routine and routine-run ids, name, creator, `deliverTo`, access, report, how it fired, the slot it was due at) and the legacy `meta.routine` `{ id, name, runId }`. The event, when there is one, stays in `routine_runs.event` and reaches the model only inside the outside-content envelope (`untrustedBlock`), never in the brief's text. Nothing of a firing appears in the routine's conversation; the run strip in Rotinas is its history.

The background run's context: the routine block (instructions, access level and what it allows, report policy, slot and how late it runs, the last run's record in the envelope, the event in the envelope) and a read-only view of the recent messages of the conversation it reports to, so it knows what people already said.

`hand_off` delivers its `routine_handoff` notice to `deliverTo` (refs carry `routineId`, `routineName`, `routineRunId`, `runId`), never to the room, at once and once, and only while its routine run is still open (one stopped, replaced or given up meanwhile delivers nothing). Before delivering it re-checks that the routine still exists and is active (a one-off or a manual run counts as live) and that its creator can still post there; if not, the routine run is skipped with the reason and the model is told to finish. The notice wakes an unattended run of the same agent there: it never joins a run working for a person (a person's own words do join; an agent's message for one person joins only a run working for that person; a report or a note joins only a run such news woke), and its text reaches the model inside the outside-content envelope. Approval cards a routine run asks for are posted in `deliverTo`, never in the room.

### 5. The routine ledger

`routine_runs.status`: `queued` → `starting` (claimed) → `started`, then exactly one end: `reported`, `silent`, `failed` (with `code`), `canceled` (a person stopped it), `superseded` (the next slot replaced it while it waited), `missed` (it couldn't run in time); `skipped` when a slot never started a run. `closeRoutineRun` is the only place a routine run ends, called on every ending of a background run: its answer, a failure, a stop, a deploy, a computer cut off, a supersede. A background run never posts by itself on any path (stop, interruption, deploy recovery, approval suspend): the only things a routine puts in a conversation are its `hand_off` notice and its approval cards. A reaper closes rows whose agent run ended and fails `queued` rows whose job died. `routine_runs.brain` records the brain that ran it, `message_id` the agent's message people saw, `finished_at` when it ended.

### 6. Firing rules

In order, for each firing:

1. **Claim** the row (`queued` → `starting`) atomically; transient errors retry the job, permanent ones fail the run.
2. **Structural checks pause the routine** with a coded `paused_reason` and one notification: creator gone or no longer able to post there (`creator_left`, `creator_no_access`), agent archived (`agent_archived`), agent no longer in the channel (`agent_not_in_channel`), audience (`audience`). Removing a member pauses their routines at once. An admin or the agent's owner can take a routine over.
3. **One run at a time per routine.** If the previous run is still queued or working, the slot is `skipped` (`previous_running`). If it waits for a person (an approval or answer) since before the previous slot, it gives way: it is `superseded` (its approvals expire) and the new one starts; otherwise the slot is skipped (`previous_waiting`). Event routines never run in parallel either: events arriving while a run is queued merge into it; while one runs, they gather in one waiting run that starts when it ends.
4. **Computer away.** A background run never falls back to the API brain. It waits for its computer; the next slot supersedes the waiting run (the freshest slot is the one that runs when the computer returns). A waiting run whose slot is more than 12 hours old when the computer returns is `missed` instead of running. The creator and the agent's owner hear it once per outage (grouped, resolved by the next good run), and Rotinas shows "waiting for <computer>". A run that resumes is told its slot and how late it is.
5. **Limits.** A routine that starts agent runs fires at most every 15 minutes (`routine.too_frequent`; reminders are exempt); an agent has at most 20 active routines (`routine.too_many`). Events carry a dedupe key (provider delivery id, issue id): the same event never fires a routine twice. An `issue.created` routine never fires for an issue a routine or unattended run created, and only for issues its creator can see; the event carries the issue id, not its title.
6. **Fatigue.** A failure counts in `failures_in_row`; the first failure after a good run notifies (one notification per routine and streak), the fifth in a row pauses the routine (`failing`) with one notification; a good run resets it.
7. **Stop.** Rotinas has Stop for a running routine (the background run is canceled quietly, the row ends `canceled` with who stopped it); pausing or deleting a routine also stops its run in progress.
8. **Email.** New mail merges only into a queued run whose job is still alive; when an email-triggered run fails or is canceled, its emails are released so the next run gets them.

Schedules keep one semantics for times that don't exist on a DST change (move forward), and an edit keeps the routine's own time zone unless one is given.

### 7. When a routine speaks

`routines.report`: `when_new` (the default: the agent judges; when the instructions ask for a report every time, there always is one) or `always` (a report on every run). With `always`, a run that ends without `hand_off` but with a final text delivers that text as its report (`auto_report`); with no text it fails (`no_report`). The run woken by a report tells people in the agent's voice, like a colleague in the chat: the news itself first (a greeting on the day's first message in the morning, never a verdict on the run such as "quiet run, nothing urgent"), the concrete findings (ids, numbers, links) even when it asks for a decision, what it would do only when there is something to do, without redoing the routine's lookups; a routine that reports every time keeps the full report. Its message carries `meta.routine` (`id`, `name`, `routineRunId`, `noticeId`) and the routine run records it in `message_id`, so the app shows the message tagged with the routine (the notice it answers folds into it) and Rotinas links each run to it.

### 8. Approvals carry their reason and their origin

Every tool that opens an approval, and `ask_user`, takes a required `why` (what the agent found and why this action), added to the tool's schema by the gateway for every brain and checked on every call (empty or too short is refused with the reason). It is stored on `approvals.why` and shown on the card; the model-only "explain first" nudge is removed. Approvals asked while nobody watched carry `approvals.origin` (`routine` with its name, or `unattended`) and the card and notification say so.

### 9. Privacy

Rotinas shows a routine's prompt, records and reports only to its creator, admins, the agent's owner and the members of the conversation it reports to; everyone else sees its outcomes (ok, silent, failed, skipped) without text, and no prompt for DM, Drive or private-channel routines. A notice is rendered as "yours" only in the context of the agent it is for. In the agents' DM a run only reads exchanges made for the same person, and a question for one person never joins a run working for another.

### 10. One engine, one base

- The run's effective brain is stored (`agent_runs.brain`) and read by shared code (steering, talker, continue, outages), never the agent's stored brain.
- Pause cards (approvals, questions, secrets) are posted by one function for the API loop and the bridge, so both carry the same meta, receipts and routine target.
- Computer brains get a "# This turn" block on every turn (now, why they were called, where they are; its fixed part is clipped), followed by the memory and wiki found for the trigger whole on the run's first turn (or a session started afresh); their system prompt holds only what doesn't change during a session.
- Reading a person's message to this agent during a run (one that names it, quotes it, or names no agent) means the run owes them an answer (it can't pass); one addressed to another agent in the same thread is only context. A run that changed something posts its receipts instead of passing; a message read at the tool-call cap is never lost; redispatched messages keep a trigger that matches their author; runs woken by a note sent before notes were tracked may pass, and so may an agent the router brings in on another agent's message about its routine's report. What came of a note since then (ADR 0095) is a `consult_reply`: the run it wakes resumes the work for the person behind it and must answer.
- A background run near the tool-call cap is asked to hand off what it has instead of failing.
- Background jobs never take more than half of a worker's job slots, so a person's message always finds one; queue waits are measured.

## Addendum (2026-10-31): work by default

Several ways work comes back to an agent had no person behind them, so the run they woke was `unattended`: its computer turn only read (`plan`) and the run policy hid code, git, pull requests, `ask_agent`, `tell_agent` and `post_message`. That covered the reply to the agent's own note, the end of its own background task, a person's decision on its folder request or on an agent it proposed, a routine's report, the agent's own messages, and everything those runs handed on. Agents said they would do the work and couldn't, were never told why, and hand-offs between agents stopped there. What an agent may do already has its own limits (its scopes, each tool's approvals as the workspace set them, the command policy on its computer, its audience, the stretch limits of ADR 0089), so a second, stricter set for runs nobody is behind stopped work without making anything safer that those limits don't already hold.

Whoever woke it, a run works within the agent's own permissions:

1. **Work that comes back goes on for the person behind it.** The walk (`authority.ts`) follows every link the server writes back to the run the work came from: a notice's `refs.runId` of any kind (an answer, a note's reply, a wait's result, a follow-up, and now a decision on a proposed agent, `agent-proposals.ts`), the run on a background task's end (`meta.machineTask.runId`, `machine-tasks.ts`) and on a folder decision (`meta.machineAccess.runId`, `machine-access.ts`). A link that isn't a run id, or names a run of another workspace, leads to nobody. "Continuar" keeps the person who wrote into the stopped run (`steeredBy`). Approvals and notifications go to that person, and a task's or folder's end for one person joins only a run working for that person.
2. **Nobody behind it: the agent itself.** An `unattended` run (a routine's report, an agent's own message, work either started) gets the computer profile `work`, the tools a person's run has (all but `hand_off`), the tools' own approvals (a connected app's access level, a mailbox's "send without asking", the "Aprovar sempre" rules) and its credentials as they are. A tool that acts with a person's rights refuses on its own when nobody is behind the run (DMs, reminders and routines, channels, threads, events, missions, secrets); `post_message` posts as the agent in a channel it is a member of. Its approvals go to the agent's owner and approvers as before, and the card still says nobody was watching (`approvals.origin`). A stretch's pause card (ADR 0089) for such work, which told nobody, now tells the owner of the agent it last stopped at, who may press Continuar (`notifyMessage`), in any public channel of the workspace even if they never joined it (private channels and DMs stay members-only).
3. **Only what was set to read reads.** A routine's own run set to "Só olhar e contar" (`read`, also a brief-less one) stays as it was (`plan`, reads and `hand_off`), and its routine block now says why: its creator set it to only look and tell. A mission reads before Start and while a write item is live (ADR 0044); any other run in its thread, a report's included, gets the mission's profile. Making the mission act stays with a run its owner or a decider is behind, or one the mission woke (`runActsForMission`): its plan and report tools, the computer's tools there and now also the machine tools a computer brain reaches through the bridge (`start_task`, `upload_artifact`), which the run policy used to keep from a report's run. A routine that may act keeps §2's limits and may now start the computer's background tasks: `start_task` under `sandbox:run` is code work, only the mission's own (no scope) is a mission tool. Their end is delivered where the routine reports (`deliverTo`), never in its room, where nobody would read the run it wakes. A reminder that asks the agent to do something at its time (`schedule_reminder` with `ask_agent`) is created with access `act`: nobody set it to only look.
4. **What a routine read keeps its guards one hop later.** Email and webhooks only fire routines, and a routine set to only look still reads a stranger's text and may repeat it in its report. So an `unattended` run whose chain roots in a routine (`reason` `routine_report`: its report woke it; `routine`: the end of a task a routine started, or anything either handed on) works as in §2 but keeps the three guards of a routine's own run (`fedByRoutine`): a call carrying a credential is refused and what it posts is masked, every write to a connected app asks a person, and every mail send asks whatever the mailbox allows. It also keeps within that routine (the unattended authority carries its `brief`): woken by one set to only look and tell (or one whose brief is gone) it reads and replies where it is, with the `plan` profile and no browser, desktop, code, posts elsewhere or other agents; woken by one set to act it may do what the routine may, reaching only its creator's rooms and agents (`post_message`, `send_dm` to the creator, `ask_agent`, `tell_agent`), so a `tell_agent` hop never reaches further. Neither manages routines or reminders, asks for secrets or permissions, nor uses a mission's tools. A person writing into it (`steeredBy`) lifts all of it. What a routine's notes bring back always lands where it reports, even while its run still works (`reportHandOffs`), so none is lost when that run ends unread. A routine's task end goes where the routine reports only while the routine may still speak there (`routineDeliveryBlock`: not deleted, not paused, its creator can still post); otherwise its room keeps the record and nobody is woken. The run it wakes reads the routine's report guidance and may pass when the routine reports only news.

| Kind | When | Acts as | Computer | Tools |
|---|---|---|---|---|
| `person` | A person asked, directly or through agents; work came back to a run of theirs; or a person wrote into the run | That person, within their permissions and the agent's scopes | `work` | All but `hand_off`; the tools' own approvals |
| `unattended` | No person at the root: a routine's report, an agent's own message, work either started | The agent itself; approvals and pauses to its owner | `work` (`plan` when rooted in a `read` routine) | All but `hand_off`; the tools' own approvals; what needs a person's request refuses. Rooted in a routine (§4): that routine's bounds plus the reply where it is; credentials refused and masked, a connected app's write and every mail send ask |
| `routine`, `act` | A routine's background run that may act | Nobody; its creator stays accountable | `work` | Reads, `hand_off`, internal changes and code (`start_task` too); a connected app's write asks; nothing elsewhere; credentials refused and masked |
| `routine`, `read` | A routine set to only look and tell | Nobody; its creator stays accountable | `plan`, told why | Reads and `hand_off` |

This replaces the `unattended` row of §1, the unattended bullet of §2 (and the read-only run a report of a `read` routine woke, `routineAccess`, which is gone), §3's `plan` for unattended runs and its mission paragraph, and narrows to routines and the runs rooted in them (§4) the mail rule of §2 (a send always asks) and the credential rule of §3 (a call carrying a credential is refused, what is posted is masked). The refusals that told a run "say what you'd do; a person asks you to go ahead" are gone.

What doesn't change: stretches still bound what agents start on their own (ADR 0089), with the lower limit when an agent wrote a stretch's first message; a chain nobody is behind still wakes only agents open to everyone (audience); a routine's report joins only a run such news woke; `issue.created` routines don't fire for issues a routine or a run nobody is behind created; a run woken by a note may pass.

Consequences: outside content that reaches a run nobody is behind (a routine's report, a task's output) can make it act within the agent's permissions, as the same content can a person's run, except that when a routine brought it (§4) it stays within that routine, no credential leaves and nothing reaches a connected app or a mailbox without a person. It stays inside its envelope (`untrustedBlock`), a sensitive action still asks a person, and the command policy still holds on the computer. A routine that only looks reads as before.

## Addendum (2026-11-01): a routine's message is the message

A routine set up as "every day at 08:30 give me a good morning" showed two messages: a collapsed report with the greeting inside ("Rotina «Bom dia diário» · Ver relatório"), then the run that report woke, talking about the routine ("it ran for the first time today, nothing new to report") and bringing up an unrelated question from earlier in the conversation. The hand-off path (§4, §7) suits a routine that watches something and needs the agent to act in the conversation; it doesn't suit one whose result is the message itself, which is most of what people ask routines for: a greeting, a digest, a reminder, a summary.

1. **`hand_off` posts the message.** By default its `message` is posted as-is as the agent's own message in `deliverTo` (`deliverRoutineReport`): an agent message at hop 0 with nobody behind it, `meta.routine` `{ id, name, runId }` (the same shape as a reminder's, so the app shows the routine tag, with no report to unfold), recorded in `routine_runs.message_id`. It wakes nobody: no notice, no second run, and its `message.posted` routes to nobody (no mention runs, no router), so text the routine read can't start another agent's run outside the routine's bounds. (Amended by ADR 0097's default-allow addendum: set to act, its mentions wake the agents it names, for its creator, within its bounds; the router still stays out.) The routine run is `reported`; its final text stays its record, never posted. With `always`, a final text without `hand_off` is that record, written for the next run, so it is never posted as-is: it goes as a `routine_handoff` notice that wakes the agent, as in §4 (`auto_report`).
2. **The hand-off path stays where it earns its place.** With `wake_me: true` the message is a `routine_handoff` notice as in §4, waking an unattended run there that acts or decides on it and tells the people (§7, the addendum of 2026-10-31 §4 bounds it). The routine block asks for it only when what the routine found needs the agent to act or decide in that conversation (its instructions say so, or there is work it can only do there). A `when_new` routine with no news still posts nothing.
3. **What the routine writes.** The routine block says `hand_off` posts its message as-is: the message itself, to the people, in their language; never about the routine or its runs (that it ran, that it's the first run, that there is nothing to compare with), and nothing from other conversations its instructions don't ask for. The view of what was said in `deliverTo` stays, for what people already know, and is marked as not for the message.
4. **Safety doesn't change.** A routine set to only look and tell still can't act or reach other agents (its message's mentions wake nobody), and posts nowhere but through `hand_off`, in the place its creator chose (routines may post when asked). What it read stays data inside its envelope: it may end up as text in the message, never as an action. The re-checks before delivering (`routineDeliveryBlock`) and once per run hold for both paths; a second call is refused once the routine run is `reported`.
5. **Old messages keep rendering.** A report notice and the reply that answers it (`meta.routine.noticeId`) still fold together as before; only new messages take the new shape.

This changes §4's "hand_off delivers its routine_handoff notice" (now with `wake_me` only), §5's "the only things a routine puts in a conversation are its hand_off notice and its approval cards" (its message or its notice, and its approval cards) and §7's run woken by every report (now only by a hand-off).


## Addendum 2026-11-03: a routine does its job without asking every run

The owner decided on 2026-10-31 that a routine a person asked for posts and messages where they asked, with no approval. Posting in agentes.chat already worked that way (§2 amendment), but a routine's write to a connected app still became an approval card on every run, whatever the person had asked for: a routine set up to post the weekly summary in Slack asked for that post every Monday.

1. **Its job is named when it is set up.** `routines.own_actions` lists the connected-app actions the routine's job needs: tool names as the agent calls them, or a Composio action's slug (`SLACK_SEND_MESSAGE`). The agent sets them with `create_routine`/`update_routine` (`own_actions`), from what the person asked for; the API takes `ownActions` on create and edit. Only someone who decides the agent's approvals (its owner, `approve_actions`) may set them, and only the routine's creator may change them (others take it over first). Merge, deploy, rollback and the rest of the never-for-good list (`alwaysAsks`) are refused when set.
2. **Setting it up is the approval.** On a routine's own run, the Tool Gateway lets a call through without a card (`ownJobCovers`) when every action it runs is in the list, the call could be approved ahead at all (`aheadRefusal`: a connected app's own action, never one that runs whatever its input says, never merge, deploy, rollback and the like), and the routine's creator still decides the agent's approvals. All of it is read fresh on every call, so a removed action or a creator who lost the right asks again at once.
3. **What stays a card.** Any other write to a connected app, an action beside an allowed one in the same call, merge, deploy and rollback, a mailbox's send (its owner's own rule, ADR 0038), and every write from a run a routine's report woke (§4: only the routine's own run does its job).
4. **People see it.** The agent's confirmation and the chat receipt of a created routine say what it does on its own; the routine's form and details list it ("Faz sozinha"), or say that every action in a connected app asks first.

## Addendum 2026-11-05: "Sempre nesta rotina" and merges without asking

**"Sempre nesta rotina".** A card from a routine's run offers one button in place of "Aprovar sempre": approving it adds that kind of action to the routine's `own_actions`, in the decision's transaction, so that routine's next runs do it (`ownJobCovers`) and nothing else changes. It is `approvals.approve_always` with a `routineId`, kept as own actions, never as an agent's rule. It is offered only for what `ownJobCovers` would then let through (`routineKind`): a connected app's own action, never merge, deploy, rollback and the like (`aheadRefusal`), never a deletion or a payment by its name (`neverInRoutine`), for a live routine with room that isn't a widget's and whose creator still decides the agent's approvals. A send stays offered: it is what routines are for. Commands on the computer don't get the button: `own_actions` holds connected-app actions. Undone on the routine's page, in Faz sozinha.

**Merges without asking.** `agents.merge_repos` is a per-agent list of exact repositories, set by its owner or an admin, within the agent's repositories. A merge there runs with no card, with its own audit row (`agent.merged_without_asking`) and a receipt under the reply (`pr.merged`, nothing to undo). Every other sensitive kind still asks, and so does an unknown repository.

- **Connector.** `merge_pull_request` names `owner` and `repo`, so the gateway decides (`connectorMerge`).
- **Commands.** The computer decides, atomically with running it: the server sends the list (`mergeRepos`), and a held command runs only if it is nothing but one merge (`loneMerge`) in a repository on the list (`allowedMerge`). `gh -R` or the URL names it, else every remote of the folder must be that one repository (gh may pick any of them). An older runner ignores the list and holds, so it asks. `--admin`, `--delete-branch`, `--auto`, two merges in one command and any other program beside the merge stay held.
- **`why`.** A brain's own `gh pr merge` is refused with "ask with run_code and why". With a list set, such a call goes to the computer first (`computerDecides`); held after all, the card carries the agent's reason.
- **Not covered.** Background tasks (`start_task`): a shell task's merge is held at its start and asks; inside a Claude Code or Codex task the deny list refuses it and tells the task to report, and the agent can merge when it wakes. Composio's GitHub actions keep their card. A run a routine's report woke asks, like every write of such a run (§4), and so does a mission's task, which has no run to leave a receipt on. A folder whose `gh-resolved` names a repository (`gh repo set-default`, or any `git config`) asks: gh goes by it, whatever the remotes say.

Handing the agent to a new owner clears the list, like its "Aprovar sempre" rules.

## Addendum 2026-11-09: job lanes, slots that grow, routines that ramp (§10)

What went wrong: in a busy hour, agents' runs and a burst of routines held every job slot for minutes. Quick jobs (`message.posted`, `notifications.message`, `search.index`) then waited tens of seconds behind them instead of about one, and new runs waited minutes to start, while the database, the server and the agents' computers stayed calm. The limit was the pump: 20 jobs at once per process, background work up to half, one queue for every kind.

1. **Two lanes.** `LONG_JOB_KINDS` (`outbox.ts`) lists the kinds that can hold a slot for minutes, or that sweeps queue by the hundred with nobody waiting on them: agents' runs, routines' firings, agents' own wakes (`autonomy.later`, `agent_work.check_in`, `agent.follow_up`), memory consolidation and reflection, reindexing, storage migrations, skill updates, Vault syncs and the purges. Every other kind is quick. Of the `OUTBOX_MAX_IN_FLIGHT` slots (48), `OUTBOX_QUICK_SLOTS` (12) are for quick jobs only; long jobs hold the rest at most (36), background work half of those (18). A claim takes quick jobs first, then long ones in the room left, then background ones.
2. **Slots that grow.** Every 30 s the pump looks at each lane: the p90 of its claims' waits, or its oldest job still due when that is longer. A lane that waited over 2 s gets a quarter of the base more (12), the quick lane first, up to `OUTBOX_MAX_IN_FLIGHT_CEILING` (64 by default, for a small server) and never past 4 jobs per database connection (`DATABASE_POOL_MAX`, now 20 by default; the built-in database has one, so there they never grow). A lane that waited for nothing and left that much unused gives it back, never below its base.
3. **Told when it isn't enough.** A quick lane over 5 s for 5 minutes, growing included, is reported once to the error reporter, and again only after it recovered; each resize is a log line. No page shows it: none shows the job queue today.
4. **Routines ramp.** A scheduled routine fires at its slot plus a stable offset into that minute from its id (0–59 s), and the firing tick runs every 5 s (it was 30 s, at most 100 routines a tick), so the routines of 09:00 fire across the minute instead of together. Its slot, its next run as shown and its run's `at` stay the minute.

This changes §10's last bullet: background jobs take at most half of the long slots, and quick jobs keep slots of their own. ADR 0046's priority column stays a proposal: lanes by kind need no migration.

ADR 0163 takes this further: workspaces take turns in each lane, the long lane grows as far as memory allows instead of 4 jobs per database connection, and worker processes add slots.

## Addendum 2026-11-12: Codex on Windows (§3)

Codex runs on Windows from runner protocol 60 (ADR 0032, "Codex"). There §3 holds through Windows' own isolation, not the command policy:

1. **The sandbox is MXC** (Microsoft Execution Containers, Windows 11 24H2 and later), named on every Codex process of a `plan` or `work` turn. It keeps the network out and writes to the turn's folders, with no setup. Codex picks no sandbox on Windows by itself, and its other two don't do: `unelevated` keeps the network out only through proxy variables, and `elevated` needs an administrator's setup that several Codex homes (each AI account's folder, ADR 0041) can't share. Codex's own MXC check (a command run inside MXC) decides; a computer where it fails runs no `plan` or `work` Codex turn: it fails with `windows_sandbox`, worded as what Windows needs.
2. **Nothing asks** (`approvalPolicy: never`, as `codex exec` everywhere). Codex runs its commands in PowerShell there, which the command policy doesn't read: answering its approvals with POSIX rules would let through what they can't see, and an approved command that its sandbox refuses runs again outside it. So whatever MXC refuses stays refused, and an approval Codex asks all the same is declined. So on Windows, what needs the network (a push, an install) doesn't run from Codex's own shell. Nothing else lifts MXC either, as on every system (the next addendum): no one's own Codex rules, no network and no folder beyond the agent's, whatever the Codex home's config says.
3. **The right hand** (`chat`) needs no sandbox: with none, Codex refuses every command of its own, and the turn stops at the first one anyway.
4. **Not reached yet.** MXC lets a command reach services on the computer's own loopback (Codex's documentation says so): whatever listens there, the agent browser's debugging port included, is reachable from a turn, which POSIX sandboxes refuse. The agent browser on a pipe instead of a port would close that. Background Codex tasks are refused on Windows until they run inside the same sandbox.

## Addendum 2026-11-12: a Codex home's own rules (§3)

Found while bringing Codex to Windows, and true on every system: a Codex rule could lift §3. Codex keeps rules in its home (`rules/*.rules`, written when someone picks "don't ask again") and reads a project's (`.codex/rules`) when its home trusts that project. A command every part of which an allow rule matches runs outside the sandbox, with the network, and Codex asks nobody, so the command policy never sees it. On the computer's own sign-in, a person's `git push` allow could push to the default branch with no hold, in a `work` turn and in a routine's `plan` turn alike.

1. **No one's own rules.** Every `codex exec` turn and background task passes `--ignore-rules` (Codex 0.122.0 and later), as the right hand's turns already did. The app-server can't leave them out, so a turn where Codex would load some (in its home, or in a folder at or above the turn's when that home trusts a project: an AI account's home trusts none) runs on exec instead: no messages mid-turn and no approvals there, its sandbox the limit.
2. **The sandbox is ours.** Its network (off in a turn) and its writable roots (the agent's folders, an empty list when there are none) are the runner's, whatever the home's config says.
3. **The command policy reads lines as the shell does.** A `#` opening a word is a comment to its line's end, and a backslash before a newline joins two lines, so neither hides a line: a quote opened after either can't swallow the commands below it. Pushes and lone merges are read from the lines the shell runs (a newline inside quotes ends none), and a merge with a comment after it or a line continuation waits for a person.
